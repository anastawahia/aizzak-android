# مراجعة ربط خدمات الحساب — ACCOUNT-CONTEXT-01

الإصدار: 1.0. التاريخ: 2026-10-31. الحالة: `awaiting_human`؛ التنفيذ لم يبدأ.

هذا استكمال للمتطلبات والتصميم المعتمدين في 2026-10-30، وليس إعادة تصميم للتطبيق. النطاق هو إكمال جلب سياق الحساب، فتح الرئيسية والحساب بعد نجاحه، والخروج وتغيير كلمة المرور وفق الرحلة المعتمدة. الوكلاء الثلاثة يبقون بحالة «متاح لاحقاً».

## القرار الأول: بيئة التطوير

المقترح تنفيذ الربط واختباره على خادم WSL المحلي الموصوف في `/home/AIZZAK/CLAUDE.md` بوصفه بيئة التطوير الحالية. لا يوجد عنوان إنتاج ناجح جرى التحقق منه؛ العنوان المذكور في وثائق النشر `https://api.aizzak.com` لم يُحل عبر DNS.

- تشغيل تبعيات nginx والتطبيق حسب Compose والتحقق من الجاهزية، دون حذف بيانات أو تشغيل اختبارات تفريغ الخدمات المشتركة.
- بعد التحقق من وصول Windows إلى منفذ WSL رقم 80، تمريره للهاتف عبر USB باستخدام `adb reverse tcp:8080 tcp:80`.
- عنوان debug: `http://127.0.0.1:8080/api/v1/`. السماح بـHTTP محصور في إعداد debug ولمضيف loopback المحدد؛ لا سماح عام بـcleartext.
- نسخة release تظل HTTPS فقط، وتتطلب عنواناً مطلقاً معتمداً قبل اختبار الربط أو تسليم إصدار متصل. لا يُكتب فيها عنوان إنتاج مفترض، ولا يُعطّل التحقق من الشهادات.
- لا تُعرض عناوين الخادم أو إعدادات التطوير في واجهة المستخدم.

البديل: تزويد عنوان HTTPS عامل وموثوق للشبكة التي يصل إليها الهاتف، ثم استخدامه بدلاً من تمرير USB. لا نشر أو تعديل DNS ضمن هذه المهمة.

## القرار الثاني: فصل الخروج المعتاد عن الحظر الأمني

الخروج الحالي يحظر Firebase UID كاملاً إلى نهاية صلاحية الرمز تقريباً، ويمنع الدخول الجديد من الوصول للخادم. المصدر يصف ذلك كأداة لإيقاف جلسة مخترقة. هذا الأثر يحتاج قراراً صريحاً قبل ربط زر «تسجيل الخروج» به.

المقترح أن يبطل الخروج المعتاد **رمز ID المستخدم في الطلب**، وأن يبقى الحظر الإداري الشامل آلية منفصلة محفوظة. التغيير يمس سياسة التفويض في الخادم، ويستلزم مراجعة أمنية مستقلة واختبارات عدم تجاوز الحظر. لا يكفي تجاهل طلب الخروج الخلفي في Android أو تجديد الرمز لتجاوز قائمة الحظر.

يبقى شكل الواجهة `POST /api/v1/me/logout` و204، ويحاول Android استدعاءها مرة محدودة ثم ينفذ خروج Firebase وتنظيف بيانات الحساب في جميع حالات الفشل. لن يُعلن إبطال رموز التحديث أو جميع أجهزة الحساب من دون آلية خلفية مثبتة لهذا المعنى.

الآلية المقترحة بعد المراجعة الأمنية:

- إبقاء `SessionRevocationList` الحالية للحظر الإداري وتعطيل الحسابات، دون مسحها عند دخول المستخدم.
- قائمة منفصلة لبصمة SHA-256 للرمز المصدّق؛ مدة بقائها نهاية صلاحية الرمز مع هامش التحقق. لا تخزين أو تسجيل للرمز الخام.
- فحص القائمتين في مسار المصادقة المركزي قبل استخدام نتيجة principal مخزنة، وإبقاء فشل مخزن الحظر سبباً لرفض الطلب.
- رمز جديد مختلف يمكنه الدخول بعد الخروج؛ إذا أعاد Firebase الرمز نفسه بايتياً خلال الثانية نفسها فسيبقى محظوراً. لا وعد بقبول كل دخول جديد فوراً دون هذا القيد.
- هذا يبطل الرمز المقدم فقط؛ لا يبطل عائلة refresh tokens، ولا كل رمز سابق على الجهاز، ولا يغلق WebSocket قائم بالضرورة. إبطال جلسة كاملة لكل جهاز يحتاج عقد جلسات منفصلاً، ولا يضاف ضمنياً لهذه المهمة. تتولى Firebase إنهاء الهوية المحلية في Android.

هذه حدود قرار الاعتماد، وليست نتيجة تنفيذ. المراجعة المستقلة قبل التنفيذ موثقة في [security-design-review.md](security-design-review.md).

## ربط Android ضمن التصميم المعتمد

```text
استعادة Firebase
  ├─ لا هوية → تسجيل الدخول
  ├─ بريد غير موثق → التحقق من البريد
  └─ هوية موثقة → تحميل سياق الحساب
                      ├─ نجاح صالح → الرئيسية / الحساب / الإعدادات
                      ├─ 403 → رفض وصول واضح
                      └─ شبكة / خدمة / رد غير صالح → إعادة محاولة / خروج
```

- `AuthViewModel` ينسق حالة الجلسة الحالية. سياق الحساب في الذاكرة فقط، دون صلاحيات افتراضية أو تخزين رموز يدوي.
- `IdTokenProvider.getIdToken(expectedUid, forceRefresh)` يرفض الرموز المتأخرة أو التابعة لحساب تغير أثناء الطلب.
- `AccountContextRepository.load(expectedUid)` يحول DTO منفصلاً إلى `AccountContext(userId, workspaceId, roles, permissions)`؛ `logout(expectedUid)` محاولة محدودة دون تكرار تلقائي للكتابة.
- `LOADING_CONTEXT`, `READY`, `ACCESS_DENIED` تضاف إلى حالات الجلسة. `READY` يتطلب سياقاً صالحاً مرتبطاً بالهوية الحالية. إنشاء الحساب أو مجرد توثيق البريد لا يمنحان الوصول وحدهما.
- 401 يجدد الرمز مرة واحدة ويعيد GET الآمن مرة واحدة؛ استمرار 401 ينهي الجلسة المحلية مع رسالة واضحة. 403 يبقي الهوية ويعرض رفض الوصول، دون منح صلاحيات أو حلقة دخول.
- إلغاء طلبات الحساب ومسح السياق فور الخروج أو تبديل الهوية؛ تجاهل النتائج المتأخرة حتى إن لم يحترم النقل الإلغاء.
- لا تخلط معرف المستخدم الخلفي وFirebase UID. البريد من Firebase؛ الاسم اختياري، ولا يُستنتج من اسم Workspace.
- إعادة استخدام تصميم Home/Account/Settings والتنقل المعتمد. عند إتاحة Account، ينفذ تغيير كلمة المرور رحلة Firebase الحقيقية لإعادة التحقق والتحديث؛ لا زر دون فعل ولا تحويل صامت إلى استعادة البريد.

## معايير القبول وخطة التحقق

1. هوية موثقة وسياق صالح يفتحان الرئيسية؛ نقص حقل إلزامي أو خطأ أو رفض لا يفتحها.
2. فحص شكل المورد المباشر ومعرفات UUID والقوائم الفارغة والقيم غير المعروفة دون منح افتراضات محلية.
3. 401 ثم نجاح، 401 متكرر، 403، مهلة، قطع شبكة، رد غير صالح و429؛ الحفاظ على الإلغاء ومنع التكرار.
4. خروج دون شبكة، تبديل حساب أثناء الطلب، ونتيجة متأخرة من الحساب السابق لا تُظهر بياناته.
5. نجاح الخروج الخلفي يرفض الرمز المقدم، ويقبل رمزاً جديداً مختلفاً؛ اختبار قيد الرمز المتطابق في الثانية نفسها، وبقاء الحظر الإداري وتعطيل الحساب نافذين حتى على الرموز الجديدة.
6. فحوص كلمة المرور لا تسجل أو تحفظ الأسرار؛ فشل إعادة التحقق لا ينفذ التغيير، والنجاح نتيجة SDK فعلية.
7. فحوص JVM وعقود HTTP معزولة، ثم debug build وlint وتجميع واختبارات Compose على جهاز متاح. تمييز الاختبارات المعزولة من اتصال حساب حقيقي.
8. فحص دمج manifest/network configuration: لا HTTP في release، ولا trust-all TLS أو logging لرموز/أجسام حسابات، ولا cache لحسابات المستخدمين.
9. اختبارات الخادم المعزولة والمراجعة المستقلة بحسب الملفات المتأثرة؛ لا اختبارات live قد تمسح بيانات الخدمات، ولا نشر إنتاج.
