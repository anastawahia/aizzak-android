# مراجعة أمنية لتصميم ربط الحساب

المهمة: ACCOUNT-CONTEXT-01. التاريخ: 2026-10-31.
المراجع المستقل: `/root/auth_design_review`، دور `security-reviewer`.
الحالة: `partial` — المقترح المحدد أدناه مقبول ضمن حدوده الفنية للمراجعة البشرية، والتنفيذ مشروط باعتماد السياسة؛ ليس تدقيقاً أمنياً شاملاً أو نجاح اختبارات.

هذا سجل أمين لمخرجات المتخصص الفعلية. لم يعدل المراجع أي ملف أو يشغل بناءً أو اختبارات أو خدمات أو يستعمل حساباً حقيقياً. المنسق كتب السجل بعد قراءة مخرجاته.

## النتائج والقرار المقترح

1. حافظ على `android:allowBackup=false` وHTTPS لنسخة release وعزل نتائج الحسابات المتأخرة. فتح الرئيسية مشروط بسياق صالح؛ لا صلاحيات افتراضية.
2. `/me/logout` الحالي يحظر الهوية بأكملها، ويمنع الدخول برمز جديد إلى نهاية مدة الحظر. هذا أثر مقصود في كود الخادم، ويحتاج فصله عن الخروج الاعتيادي إذا اعتُمد المقترح.
3. إبطال الرمز المقدم عبر مفتاح منفصل يحوي SHA-256 للرمز المصدّق مقبول بوصفه **إبطال ذلك الرمز فقط**، مع TTL حتى نهاية صلاحيته وهامش التحقق، دون حفظ الرموز الخام.
4. يُحفظ حظر الـsubject للإدارة والحسابات المعطلة. يفحص middleware القائمتين قبل principal cache، ويفشل مغلقاً عند تعطل مخزن الحظر.
5. لا تُفسر بصمة الرمز كإبطال كامل لجلسة الجهاز أو refresh-token family. الرموز الأخرى السابقة أو refresh token مسروق أو WebSocket قائم لا يشملها هذا الضمان. الرمز المطابق بايتياً خلال الثانية نفسها يبقى محظوراً؛ رمز مصادق مختلف يمكن قبوله.
6. يحتاج الإبطال الكامل لكل جهاز عقد جلسات مستقل؛ cutoff بحسب subject/auth_time أوسع ويؤثر في أجهزة أخرى، ولا يوفر معرف جلسة لكل جهاز.

تعرف [وثائق Firebase الرسمية](https://firebase.google.com/docs/auth/admin/manage-sessions) الفرق بين ID tokens قصيرة العمر وrefresh tokens وآلية الإبطال الإداري. لا تعني مراجعة الوثيقة أن مشروعنا نفذ أو اختبر إبطال refresh tokens.

## اتصال التطوير

استثناء HTTP في debug فقط ولـloopback المحدد، عبر `adb reverse` على جهاز تطوير موثوق، مقبول كقرار تطوير محدود. يجب:

- التحقق من عنوان الخدمة في البناء/العميل ورفض HTTP خارج 127.0.0.1 أو localhost المحدد.
- إعداد network-security خاص بـdebug ومحدد النطاق؛ لا علم cleartext عام ولا trust-all TLS أو تجاوز hostname.
- رفض إعادة توجيه رمز الحساب إلى أصل آخر؛ لا توسيع نشر منفذ الخادم إلى LAN بسبب هذا الربط.
- إبقاء release بـHTTPS وفحص merged manifest وإعداداته الفعلية. لا وصف اتصال ADB المحلي بأنه مشفر من طرف إلى طرف.

## الحالات المطلوبة قبل قبول التنفيذ

- السياق الصحيح وحده يفتح Home؛ المفقود أو المشوه لا يفتحها.
- 401: تجديد واحد وGET واحد إضافي؛ 403 رفض مستقل.
- عزل تغيير الحساب والإلغاء والنتائج المتأخرة والرموز المتأخرة.
- خروج محلي مضمون عند غياب الشبكة والمهلة وفشل الخادم.
- رفض الرمز المقدم بعد الخروج، وقبول رمز مختلف جديد، واستمرار حظر subject الإداري لكليهما.
- فشل مخزن الحظر مغلق حتى مع principal cache، وعدم وجود رموز خام في مفاتيح Redis أو السجلات.
- اختبار الرمز المتطابق في الثانية نفسها وتوثيق النتيجة.
- فحص release للتأكد من غياب أي استثناء نقل خاص بالتطوير.

الحد الأدنى لاعتماد المستخدم هو تغيير نطاق إبطال الخروج واتصال debug المحلي. بقية متطلبات السياق والتحقق والذاكرة و401/403 ورصد النتائج المتأخرة تبقى ضمن اعتماد التأسيس السابق.
