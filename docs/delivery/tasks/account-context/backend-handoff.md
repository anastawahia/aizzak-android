# تسليم إلى مطور الباك إند — ربط حساب Android

التاريخ: 2026-10-31. المشروع: `/home/AIZZAK` داخل WSL `Ubuntu-24.04`. الفرع المحلي: `codex/account-context`، مبني على `master` عند `4bc6417`. التعديلات موجودة في شجرة العمل، دون commit أو push أو نشر إنتاج.

## المشكلة الحالية المطلوب حلها

تطبيق API لا يكمل الإقلاع لأن Vault يرفض تسجيل دخول AppRole. الأخطاء المرصودة في سجل الإقلاع:

```text
hvac.exceptions.InvalidRequest: invalid role or secret ID
hvac.exceptions.Forbidden: permission denied
POST http://vault:8200/v1/auth/approle/login
gunicorn.errors.HaltServer: Worker failed to boot.
```

مسار الفشل: `create_production_app` ← `CompositionRoot.from_env` ← `build_vault` ← `create_vault_client` ← `client.auth.approle.login`.

هذه أخطاء مصادقة داخلية بين API وVault، قبل تقديم خدمات الحساب، وليست دليلاً على فشل تسجيل دخول المستخدم في Firebase. رُفض الزوج الحالي عند إعادة تشغيل الخدمات، واستمر الرفض بعد إعادة إنشاء app من إعداد Compose الحالي. لم يُثبت هل السبب انتهاء `secret_id` أو استنفاد استعمالاته أو عدم تطابق المعرّفات أو إعداد سياسة آخر؛ يلزم فحصها لدى مالك الأسرار. لا يكفي restart لتحديث متغيرات حاوية قائمة.

Vault واشتراطات بدء Compose اشتغلت، لكن app يفشل ويعيد الإقلاع؛ لذلك لم تنجح فحوص الصحة الحالية، وnginx غير صحي لغياب upstream جاهز. أُوقف app وحده لتجنب تكرار محاولات الدخول الفاشلة. التبعيات باقية، ولم تُحذف أحجام بيانات.

المطلوب من مطور الباك إند:

1. التحقق الآمن من وضع AppRole: `VAULT_TOKEN` فارغ عند اختيار هذا الوضع، و`VAULT_ROLE_ID` يطابق الدور المثبت بواسطة bootstrap، و`VAULT_SECRET_ID` صالح وغير منتهٍ أو مستنفد. تصحيح/تجديد القيمة في بيئة التشغيل دون إرسالها أو طباعتها في التقرير. مرجع الإجراءات: `docs/quickstart.md` القسم 5 و`docs/stack-commands.md` القسم د.
2. بعد تصحيح الإعداد، إعادة إنشاء app لالتقاط البيئة الحالية، دون حذف بيانات أو تعطيل Vault:

```bash
cd /home/AIZZAK
docker compose up -d --no-deps --scale app=1 --force-recreate app
docker compose ps app nginx
curl --fail --max-time 5 http://127.0.0.1/health
curl --fail --max-time 5 http://127.0.0.1/health/ready
```

الانتظار حتى جاهزية الإقلاع قبل الحكم على الفحوص. إن صار app جاهزاً وبقي nginx يفشل، تُراجع وصلة upstream قبل إكمال الاختبار.

3. إثبات HTTP 200 للمسارين أعلاه، و401 لطلب `/api/v1/me/context` بلا مصادقة، ثم نجاح رحلة حساب حقيقي من Android. الصحة وحدها لا تثبت الوصول إلى كل أسرار المستأجرين. لا تُرسل رموز المستخدم أو كلمة مروره أو محتوى `.env`.

لم يقرأ منفذ ربط Android محتوى `.env` أو مخزن `vault-init` أو أسرار Vault؛ تعليمات `CLAUDE.md` تحظر قراءة مخزن التهيئة وتترك ضبط القيمة الحقيقية للإنسان. لم تُعدل إعدادات Vault أو سياساته ضمن هذه المهمة.

## تعديلات الباك إند المنفذة وسببها

| التعديل | الملفات | السبب والنتيجة |
|---|---|---|
| فصل الخروج الاعتيادي عن الحظر الإداري | `src/app/framework/auth/revocation.py` | أضيفت `TokenRevocationList` بمفاتيح `auth:revoked-token:<sha256>` في مخزن Redis المحتفظ الحالي، مع بقاء `SessionRevocationList` و`auth:revoked:<sub>` للإدارة. السلوك القديم كان يحظر Firebase UID كله، فيرفض حتى دخولاً جديداً بعد logout. السلوك الجديد يبطل الرمز المقدم فقط دون تخزين bearer خام. |
| فحص الإبطال قبل principal cache | `src/app/api/middleware/auth.py` و`src/app/api/v1/dependencies.py` | التحقق من توقيع الرمز أولاً، ثم فحص الحظر الإداري وحظر الرمز حتى عند وجود principal مخزن. بصمة الرمز وانتهاؤه يتبعان الطلب الحالي؛ يمنع cache من تجاوز الإبطال أو استعمال بصمة طلب سابق. تعطل المخزن لا يمنح وصولاً. |
| تحديث مسار logout وربط الاعتماد | `src/app/api/v1/routers/me.py` و`src/app/api/main.py` | `POST /api/v1/me/logout` ما زال يعيد 204 عند النجاح، لكنه يبطل البصمة الحالية بدلاً من subject. مدة الحظر حتى انتهاء الرمز مع هامش 60 ثانية وسقف 3660 ثانية. حقن القائمة الجديدة في app.state عبر المخزن الموجود؛ فشل كتابة الإبطال لا يُعرض نجاحاً. |
| إغلاق تجاوز أمني لتمثيل JWT | `src/app/infrastructure/auth/firebase_auth.py` | المراجعة المستقلة أثبتت أن PyJWT يقبل تمثيلات نصية مختلفة للتوقيع نفسه، مثل padding، فتختلف بصمة النص ويمكن تجاوز حظره. أضيف بعد التحقق من التوقيع والمطالبات اشتراط ثلاثة مقاطع base64url معيارية، بلا padding، وبإعادة ترميز مطابقة. التمثيلات البديلة تُرفض قبل قبول الهوية وحساب البصمة. |
| اختبارات الانحدار | `tests/unit/test_api_auth.py` و`test_auth_revocation.py` و`test_firebase_auth.py` و`test_redis_split.py` | تثبت رفض الرمز المبطل، قبول رمز مختلف صالح، بقاء حظر الإدارة، فحص الإبطال مع cache، حدود TTL وفشل Redis. اختبارات بمفاتيح RSA اصطناعية تثبت قبول المكتبة للتمثيلات البديلة ثم رفض المحول لها. |
| توثيق السياسة | `docs/design/03-api-spec.md` و`05-rbac-config-secrets.md` و`openapi.yaml` و`docs/delivery/account-context/status.md` | لتطابق وثائق العقد أثر logout وحدوده وشرط ترميز JWT؛ لا تغيير خفي في معنى الخروج. |

`GET /api/v1/me/context` كان موجوداً؛ ربطه في Android هو الجزء الجديد، ولا تعديل في شكل استجابته. لا ترحيل قاعدة بيانات أو تغيير مخطط SQL ضمن هذه المهمة.

## حدود سياسة الخروج

الإبطال يخص ID token المقدم فقط؛ لا يبطل عائلة refresh tokens، أو كل رموز الأجهزة، أو WebSocket قائماً. رمز جديد مختلف ومصدق للهوية نفسها يمكن أن يعمل بعد logout، ما لم يوجد حظر إداري/تعطيل. إذا أعاد Firebase الرمز نفسه حرفياً خلال الثانية نفسها، يبقى مرفوضاً حتى انتهاء الإبطال. لا يُمسح حظر الإدارة عند الدخول.

## التحقق والتسليم

- الباك إند: 232 اختباراً محدداً ناجحاً، بلا failures/errors/skips؛ Ruff format/check ناجحان، mypy ناجح على 490 ملفاً، وتسعة عقود استيراد ناجحة. يوجد تحذير Starlette/httpx قديم واحد. لم تُشغل الحزمة الكاملة أو اختبارات live التي قد تمسح الخدمات المشتركة أو فحص Prometheus.
- المراجعة الأمنية المستقلة اكتملت بعد إصلاح تجاوز JWT؛ لا ملاحظة حرجة معلقة في النطاق المراجع.
- بُنيت صورة التطوير من المصدر المصحح وأُعيد إنشاء app. بصمة ملف Firebase verifier داخل الحاوية تطابق المصدر المراجع: `78731602e38677c302e6685f75c367e43d4b36b6809a5957ae1118d0a907a917`.
- Android: البناء و54 اختبار JVM و15 اختبار واجهة على Samsung/API 35 ناجحة؛ Lint بلا أخطاء و27 تحذيراً. النسخة النهائية مثبتة وتفتح شاشة تسجيل الدخول. الاختبارات تستعمل fakes؛ لا ادعاء بنجاح سياق حساب حقيقي أثناء عطل Vault.
- ربط التطوير: `http://127.0.0.1:8080/api/v1/` عبر `adb reverse tcp:8080 tcp:80`. استثناء HTTP محصور في debug والـloopback. رابط الإنتاج الموثق `https://api.aizzak.com` لم يُحل عبر DNS في الفحص السابق؛ لا عنوان إنتاج عامل مثبت هنا.

نقطة الاستئناف: بعد إصلاح AppRole وإثبات جاهزية API، يعاد ربط ADB وتُختبر رحلة الدخول الموثق ← context صالح ← الرئيسية، ثم logout وإعادة الدخول. لا حاجة لإعادة تصميم شاشات Android أو تجاوز تحقق المصادقة.
