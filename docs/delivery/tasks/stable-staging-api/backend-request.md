# طلب إلى مطور الباك إند — توفير بيئة Staging ثابتة عبر HTTPS لتطبيق Android

التاريخ: 2026-11-06  
الطالب: فريق Android  
المهمة: `STABLE-STAGING-API-01`  
الأولوية: عالية لثبات بيئة التطوير والاختبار

## الملخص

نطلب توفير عنوان API ثابت ومتاح عبر HTTPS لبيئة staging، بحيث يستطيع تطبيق Android الوصول إليه مباشرة من الهاتف دون الاعتماد على جهاز التطوير أو USB أو `adb reverse`.

يجب أن يكون العنوان النهائي أصلاً مطلقاً ينتهي بالمسار التالي:

```text
https://<staging-host>/api/v1/
```

سيُمرر العنوان إلى بناء Android بواسطة `AIZZAK_API_BASE_URL` بعد أن يؤكده مالك الباك إند ويجتاز فحوص القبول أدناه. هذا الطلب لا يصرّح لفريق Android بتعديل أو نشر الباك إند.

## المشكلة الحالية

نسخة Android debug تستخدم حالياً:

```text
http://127.0.0.1:8080/api/v1/
```

ويعتمد وصول الهاتف إلى API المحلي على:

```text
adb reverse tcp:8080 tcp:80
```

هذا التحويل مرتبط بجلسة ADB ويختفي عند إعادة تشغيل Windows أو ADB أو فصل USB وإعادة توصيله. بعد إعادة تشغيل جهاز التطوير في 2026-11-06 كانت حالة البيئة كما يلي:

- الهاتف Samsung SM-A155F متصل ومخوّل عبر ADB.
- `GET http://127.0.0.1/health` أعاد 200.
- `GET http://127.0.0.1/health/ready` أعاد 200.
- `adb reverse --list` كان فارغاً.
- تطبيق Android نجح في Firebase، ثم عرض `We couldn’t load your account` لأن `/api/v1/me/context` لم يكن قابلاً للوصول من الهاتف.

إعادة إنشاء التحويل تعالج الجلسة الحالية فقط، لكنها لا تلغي الاعتماد على جهاز التطوير وUSB. لذلك نحتاج بيئة staging مستقلة ذات DNS وTLS صالحين.

## السلوك المطلوب

1. توفير اسم مضيف ثابت لبيئة staging، متاح من الإنترنت أو من الشبكة المعتمدة للهاتف دون USB أو ADB.
2. تقديم API عبر HTTPS فقط، بشهادة TLS وسلسلة ثقة صالحتين على Android API 26 فما فوق، دون CA مخصص على الهاتف ودون تجاوزات TLS.
3. إبقاء بادئة API عند `/api/v1/` وعدم استخدام redirect لتصحيح الأصل أو المسار.
4. إبقاء عقد المصادقة الحالي: Firebase ID token في `Authorization: Bearer <token>`، مع issuer/audience/project المطابقين لتسجيل Android الحالي `android.aizzak.com`.
5. إبقاء العقود الحالية التالية دون تغيير غير معلن:
   - `GET /health`
   - `GET /health/ready`
   - `GET /api/v1/me/context`
   - `POST /api/v1/me/heartbeat`
6. استخدام بيانات staging معزولة عن الإنتاج وعدم نسخ أسرار أو بيانات مستخدمين حقيقية إلى التقرير أو الرد.
7. توفير طريقة تشغيل ونشر يملكها فريق الباك إند، مع تعريف واضح للفرع/الإصدار المنشور ومالك البيئة وآلية استعادتها بعد إعادة التشغيل.
8. تأكيد حدود التوافر ومعدل الطلبات وأي قيود شبكة أو allowlist يحتاج فريق Android معرفتها.

## عقد `/me/context` المطلوب تأكيده

يرجى تأكيد أن الاستجابة الناجحة تحافظ على الشكل الحالي الذي يعتمد عليه Android، بما يشمل معرف المستخدم، معرف مساحة العمل، الأدوار والصلاحيات. لا نطلب إضافة صلاحيات افتراضية أو تجاوز المصادقة عند غياب السياق.

السلوك المتوقع:

- رمز Firebase صالح وسياق صالح: HTTP 200 و`application/json` بالعقد الحالي.
- غياب الرمز أو رمز منتهي/غير صالح: HTTP 401 و`application/problem+json`.
- هوية صحيحة دون وصول: HTTP 403 و`application/problem+json`.
- فشل داخلي أو عدم جاهزية الاعتمادات: استجابة 5xx صريحة؛ لا تُعاد استجابة نجاح ناقصة.

## خارج النطاق: `/me/logout`

هذا الطلب **لا يطلب أي تعديل** على `POST /api/v1/me/logout` ولا يعتمد عليه تطبيق Android.

العقد العامل الحالي على `master` يحظر Firebase UID مؤقتاً على جميع الأجهزة، ولذلك يبقى خروج Android محلياً فقط ولا يستدعي هذا المسار. أي تغيير مستقبلي لعقد الخروج يحتاج طلباً ومراجعة واعتماداً منفصلين، ولا يجوز إدخاله ضمن إنشاء staging.

## متطلبات الأمان والتشغيل

- HTTPS صالح فقط؛ لا HTTP ولا شهادة self-signed ولا تعطيل للتحقق من الشهادة.
- لا credentials أو token أو user-info أو query أو fragment داخل عنوان الأصل.
- عدم تسجيل bearer tokens أو البريد أو محتوى سياق الحساب في السجلات أو أدلة التسليم.
- إبقاء التحقق من المصادقة والصلاحيات فعالاً كما في البيئة الحالية.
- عدم فتح واجهات إدارية أو Vault أو Redis أو قواعد البيانات للإنترنت.
- عدم استخدام بيانات الإنتاج لإثبات القبول؛ استخدم حساب/tenant اختبار معتمدين من مالك البيئة.
- تسليم آلية مراقبة أساسية للصحة والجاهزية دون كشف معلومات حساسة.

## معايير القبول المطلوبة من مطور الباك إند

يرجى تنفيذ وتوثيق الفحوص التالية من بيئة مستقلة عن جهاز التطوير المحلي:

1. اسم المضيف يحل عبر DNS من Windows ومن هاتف Android على شبكة لا تستخدم `adb reverse`.
2. اتصال TLS ينجح بسلسلة ثقة عامة على Android API 26+، واسم الشهادة يطابق المضيف، ولا توجد redirects أو أخطاء mixed content.
3. `GET https://<staging-host>/health` يعيد 200.
4. `GET https://<staging-host>/health/ready` يعيد 200.
5. `GET https://<staging-host>/api/v1/me/context` دون مصادقة يعيد 401 و`application/problem+json`.
6. الطلب نفسه برمز Firebase صالح لحساب اختبار موثّق يعيد 200 وعقد السياق الحالي.
7. رمز منتهي أو غير صالح يعيد 401، وهوية صحيحة بلا وصول تعيد 403.
8. `POST /api/v1/me/heartbeat` يعمل وفق العقد الحالي لحساب الاختبار.
9. يبقى API متاحاً بعد إعادة تشغيل خادم/عامل staging وفق إجراء التشغيل الموثق، دون الاعتماد على Windows أو WSL أو USB الخاص بمطور Android.
10. لا يتطلب اختبار Android فتح منفذ محلي أو تشغيل `adb reverse`.
11. لا يتغير سلوك `/me/logout` ولا يُستدعى ضمن فحوص رحلة Android الاعتيادية.

بعد استلام الرد، سيبني فريق Android نسخة debug باستخدام أصل HTTPS المؤكد، ثم يتحقق على الهاتف من الرحلة التالية دون USB forwarding:

```text
تسجيل دخول Firebase موثّق
→ GET /api/v1/me/context
→ Home / Account / Settings
→ خروج محلي فقط
→ دخول فوري من جديد
```

## المطلوب في رد مطور الباك إند

يرجى إنشاء رد Markdown يذكر بوضوح:

- عنوان staging النهائي الكامل المنتهي بـ`/api/v1/`.
- هل العنوان متاح فعلياً الآن أم أنه مقترح فقط.
- اسم البيئة ومالكها وسياسة التوافر.
- الفرع وcommit/image/version المنشوران.
- مصدر شهادة TLS وفترة صلاحيتها وآلية تجديدها، دون إرسال مفاتيح أو أسرار.
- Firebase project/issuer/audience المؤكدة لرموز Android.
- نتائج معايير القبول أعلاه مع رموز HTTP ونوع المحتوى، دون tokens أو بيانات شخصية.
- أي قيود شبكة أو rate limits أو حساب اختبار يحتاج تنسيقاً منفصلاً.
- تأكيد صريح بأن عقد `/me/logout` لم يتغير ضمن هذا العمل.

المسار المقترح للرد في مشروع Android:

```text
docs/delivery/tasks/stable-staging-api/backend-reply.md
```

## حالة Android حتى وصول الرد

تبديل `AIZZAK_API_BASE_URL` إلى staging، وإزالة الاعتماد على `adb reverse` من رحلة التطوير، وأي اختبارات عقد حية تعتمد على العنوان الجديد هي أعمال **محجوبة بانتظار رد مؤكد من مالك الباك إند**.

سيبقى Android على السلوك الآمن الحالي: أصل loopback في debug فقط، HTTPS إلزامي للإصدار، خروج محلي فقط، وعدم افتراض وجود endpoint غير منشور.
