# طلب تأكيد عقد الباك إند لـ Data Search Agent

- المهمة: `data-search-agent`
- المرحلة: `build`
- التاريخ: 2026-11-06
- الحالة: **بانتظار رد مطور الباك إند**
- التغطية: `DS-REQ-01..14` والشاشات `SCR-DS-001..010`
- الجهة المرسلة: فريق Android
- الجهة المطلوبة: مالك باك إند AIZZAK العامل من فرع `master`

## سبب الطلب

تصميم Android المعتمد يعامل Data Search بوصفه وكيل RAG محادثياً داخل مساحة موجودة: سجل محادثة، إرسال وبث، مصادر معرفة، فهرسة، ونطاق استرجاع يساوي كل المصادر المفهرسة عند غياب التثبيتات أو الملفات المثبتة فقط عند وجودها.

تصف الوثيقتان المحليتان `docs/api/openapi.yaml` و`docs/api/api-specification.md` مسارات ومخططات محتملة لهذه الرحلة، لكنهما لا تثبتان أن باك إند `master` المنشور يطابقهما. كما أن الحقول العامة مثل `MessageOut.content` لا تحسم وحدها صيغة النص أو حفظ الاستشهادات واستعادتها. لذلك لا يستطيع Android تفعيل بطاقة Data Search أو بناء محولات الشبكة وfixtures على هذا الوصف قبل رد موثق من مالك الباك إند.

لم يُعدّل فريق Android أي ملف أو إعداد أو فرع أو نشر في الباك إند. هذا الملف طلب عقد فقط، وأي أسماء مسارات أدناه من العقد المحلي الحالي وتحتاج تأكيداً صريحاً؛ ليست اقتراحات لمسارات جديدة ولا إثباتاً بأنها منشورة.

## الدليل الحالي وحدوده

1. يصف العقد المحلي `GET /agents` و`GET /agents/{agent_key}`، ويعرض `AgentOut.key` و`capabilities` و`required_permissions`، لكنه لا يثبت المفتاح المنشور فعلياً لوكيل Data Search ولا إتاحته لحساب Android.
2. يصف العقد المحلي `GET /spaces`، و`GET|POST /conversations` مع `space_id` و`agent_key`، و`GET|PATCH|DELETE /conversations/{id}`، لكنه لا يثبت ترتيب القوائم أو صلاحيات المستخدم المنشورة أو idempotency إنشاء المحادثة الأولى.
3. يصف العقد المحلي `GET|POST /conversations/{id}/messages` وبث SSE عند `Accept: text/event-stream`. يصف الشرح أحداث `token|tool_call|notice|final|error` واستشهادات `rag_agent` في `final`، بينما يبقى `MessageOut.content` كائناً عاماً ولا يحدد إن كانت الاستشهادات محفوظة وقابلة للاستعادة من السجل.
4. يصف العقد المحلي `GET /models` و`PUT /conversations/{id}/model`، ولا يثبت توافرهما أو معنى الإتاحة والصلاحيات في البيئة العاملة.
5. يصف العقد المحلي `GET|POST /files` ثم الرفع إلى `upload_url` و`POST /files/{id}/complete`، و`GET|POST /knowledge/documents`، وحالات ملف وفهرس منفصلة. لا يحدد OpenAPI قائمة MIME المسموحة ولا حد الحجم الفعلي، ولا يثبت دعم `text/plain`.
6. يصف العقد المحلي `GET|POST /conversations/{id}/files` و`DELETE /conversations/{id}/files/{file_id}`، مع دلالة «لا تثبيتات = كامل corpus» و«تثبيتات = الملفات المثبتة فقط». يحتاج Android إثبات هذه الدلالة وعزلها داخل مساحة المحادثة على `master`.
7. العقد المحلي يعلن cursor موحداً وRFC 9457، ويضع `Idempotency-Key` على بعض العمليات فقط. رحلة الاستعادة بعد timeout أو موت العملية لا تزال غير محسومة لكل عملية مؤثرة.

## العقد المطلوب تأكيده أو توفيره

نرجو الرد على كل بند بالقيمة الفعلية في `master` والبيئة المنشورة، مع ذكر commit أو وسم الإصدار الذي جرى التحقق منه. إذا كان بند غير موجود، اذكر ذلك صراحة ولا تستبدله بافتراض.

### 1. اكتشاف الوكيل والصلاحيات

- ما مفتاح Data Search الدقيق؟ هل هو `rag_agent` أم قيمة أخرى؟
- كيف يميز Android بين: الوكيل غير منشور، منشور لكن غير متاح لهذا الحساب، ومتاح وقابل للاستدعاء؟
- ما `capabilities` و`required_permissions` الفعلية، وما مصدر صلاحيات الحساب الذي يجب أن يقرأه Android؟
- ما الاستجابات المستقرة للحالات 401 و403 و404/`agent.unknown` وعدم وجود credential أو model؟
- هل قائمة الوكلاء مرشحة حسب صلاحيات المستدعي أم تعرض عنصراً غير متاح مع سبب صريح؟

**قرار Android حتى الرد:** تبقى بطاقة Data Search غير قابلة للفتح، ولا يُخمن المفتاح أو الصلاحية.

### 2. المساحات والمحادثات

- أكد عقد قراءة المساحات الموجودة فقط، وترتيبها، وحقول الصفحة، و`limit` و`next_cursor`. Android لن ينشئ مساحة أو يعيد تسميتها أو يحذفها في هذا النطاق.
- أكد أن كل محادثة تنتمي إلى `space_id` واحد وأن القائمة لا تعيد محادثات من مساحة أخرى.
- أكد عمليات إنشاء المحادثة وقراءتها وإعادة تسميتها وحذفها، والحدود الفعلية للعنوان، وأكواد التعارض/الصلاحيات.
- حدد ترتيب قائمة المحادثات (الأحدث تحديثاً أم إنشاءً)، وما الحقل/المؤشر الذي يضمن ثبات pagination.
- حدد طريقة إنشاء أول محادثة مرة واحدة بعد فتح مساحة فارغة. إذا كان إنشاء المحادثة لا يقبل `Idempotency-Key`، فحدد آلية المصالحة بعد timeout حتى لا ينشئ Android نسختين.
- أكد أن حذف محادثة لا يحذف ملفات المساحة أو فهارسها.

### 3. الرسائل والسجل والبث

- قدم مخططاً مغلقاً لمحتوى رسالة المستخدم ورسالة المساعد بدلاً من الاعتماد على `additionalProperties` فقط، مع أمثلة JSON منقحة.
- أكد ترتيب `seq`، واتجاه صفحة السجل، ودلالة cursor، وكيفية تحميل الرسائل الأقدم دون تكرار أو قلب الترتيب.
- أكد عقد إرسال الرسالة: هل الاستجابة JSON أو SSE بحسب `Accept` فقط أم حسب `stream` أيضاً، وما السلوك عند التعارض بينهما؟
- أكد مخططات كل أحداث SSE وترتيبها وطرفيتها: `token` و`tool_call` و`notice` و`final` و`error`، وترميز UTF-8، والنبضات، وحالة HTTP/Problem قبل بدء البث.
- حدد معرفات المصالحة: معرف رسالة المستخدم، معرف رسالة المساعد، `conversation_id` و`correlation_id`، وكيف يكتشف Android بعد انقطاع مبهم إن كانت الرسالة قُبلت دون إعادة إرسال عمياء.
- أكد ما إذا كان الإلغاء مدعوماً لـSSE وما أثر قطع الاتصال: هل يستمر التوليد والحفظ أم يلغى؟
- أكد دلالة حذف الرسالة: هل يحذف رسالة واحدة أم turn كاملاً، وهل يعاد `204` بصورة idempotent؟

### 4. محتوى المساعد والاستشهادات

- أكد الشكل الدقيق لنص المساعد وMarkdown/code/links المسموح عرضه.
- أكد شكل `citations` النهائي: الحقول الإلزامية والاختيارية، `null` مقابل غياب المفتاح، وترتيب `rank` وهل يبدأ من 1.
- احسم أين تحفظ الاستشهادات وكيف يعيدها `GET /conversations/{id}/messages` بعد إعادة فتح التطبيق؛ وجودها في حدث `final` فقط لا يكفي لاستعادة السجل.
- أكد أن Android لا ينبغي أن يعرض `score` أو مقتطفات `/knowledge/search` بوصفها جواب المحادثة.
- حدد سلوك جواب partial أو فشل بعد وصول بعض tokens: هل توجد رسالة محفوظة، وما الحالة/الحقل الذي يميز `complete` و`partial` و`error`؟

### 5. كتالوج النماذج وتثبيتها

- أكد عقد `GET /models`: معنى `capability` و`provider` و`model` و`available`، وهل القائمة ثابتة/محدودة فعلاً.
- أكد أن `PUT /conversations/{id}/model` يقبل `ModelOut.capability` أو `null` للعودة إلى الافتراضي، مع أكواد unknown/unavailable/forbidden.
- حدد النموذج الفعلي الافتراضي للمحادثة أو الحقل الذي يسمح للواجهة بكتابة «استخدام افتراضي الوكيل» دون تخمين.

### 6. الملفات والفهرسة ونطاق الاسترجاع

- أكد تسلسل التسجيل ← PUT إلى الرابط الموقع ← الإكمال، مدة الرابط، الرؤوس المطلوبة، checksum، وسلوك انتهاء الرابط أو نجاح PUT مع ضياع رد الإكمال.
- أكد حالات الملف الفعلية وانتقالاتها (`uploaded|scanning|ready|quarantined` إن كانت صحيحة)، وما إذا كانت الحالة قابلة للمراقبة بالاستعلام أو إشعار موثق.
- أكد أن الفهرسة تبدأ صراحة فقط عبر العقد المنشور، وحالات المستند الفعلية (`pending|indexing|indexed|failed` إن كانت صحيحة)، وربط `file_id` بمستند واحد حي، وطريقة retry/reindex.
- أكد كيفية دمج صفحات الملفات والمستندات بلا التباس، وحقول التاريخ/الحالة التي تمنع عرض upload-ready على أنه searchable.
- أكد عقد تثبيت/فك تثبيت ملف للمحادثة، idempotency، ومنع cross-space pin.
- أكد بصورة صريحة: صفر تثبيتات يعني كل مصادر **المساحة نفسها** المفهرسة؛ تثبيت واحد أو أكثر يعني هذه الملفات فقط؛ حذف آخر تثبيت يعيد النطاق إلى الكل؛ التثبيت لا يمنح صلاحية قراءة جديدة.
- أكد أثر حذف ملف على جميع محادثات المساحة والتثبيتات والفهرس، وسلوك الاستبدال باسم متطابق قبل إظهاره في Android.

### 7. أنواع الملفات والحدود وإضافة النص

- قدم القائمة الفعلية لـMIME والامتدادات المقبولة في التسجيل والفهرسة، مع حد الحجم لكل ملف، حد عدد الملفات، وحصة المساحة.
- أكد أو ارفض صراحة `text/plain; charset=utf-8` لملف ينشئه Android محلياً من النص، واذكر امتداد الاسم المتوقع وحد البايتات بعد ترميز UTF-8.
- حدد سلوك content type غير مدعوم، امتداد غير مدعوم، ملف فارغ، تجاوز الحجم، quarantine، وفشل التحليل، مع status و`ProblemDetails.code` لكل حالة.
- حدد هل الاسم المتطابق يستبدل ملفاً أقدم فعلاً على `master` ومتى يحدث الحذف، لأن الواجهة يجب أن تعرض تحذيراً قبل أثر هدّام كهذا.

### 8. pagination والأخطاء والاستعادة وoffline

- أكد الغلاف `{data, meta:{next_cursor, limit}}` لكل قائمة، حدود `limit`، صلاحية cursor، الترتيب المستقر، و`common.invalid_cursor`.
- قدم قائمة الصلاحيات وأكواد RFC 9457 التي يستطيع كل مسار أعلاه إرجاعها، مع ثبات `correlation_id` ورأس `X-Correlation-Id`.
- حدد العمليات التي تدعم `Idempotency-Key`، مدة الاحتفاظ بالمفتاح، نطاقه (المستخدم/المساحة/المسار)، وسلوك إعادة المفتاح مع جسم مختلف.
- لكل عملية لا تدعم المفتاح، حدد قراءة المصالحة التي يجب تنفيذها بعد timeout/process death قبل أي retry.
- أكد أن الخادم لا يعتمد على مسودة Android ولا يعيد إرسالها؛ ستبقى المسودة محلية ومفتاحها الحساب + المحادثة. نحتاج فقط حقول السجل التي تسمح بمصالحة الإرسال الغامض.
- حدد هل توجد آلية delta/ETag أو أن offline هو cache للقراءة فقط ثم refresh كامل. لن يعتبر Android cache قديماً سلطة، ولن يعيد POST/PUT تلقائياً عند عودة الشبكة من دون عقد idempotency مؤكد.

## صيغة الرد المطلوبة

يرجى إنشاء `docs/delivery/tasks/data-search-agent/backend-reply.md` في مشروع Android، أو إرسال محتوى يسمح لفريق Android بتسجيله هناك، ويحتوي:

1. فرع وcommit باك إند المنشوران وبيئة/وقت التحقق.
2. نسخة من `/openapi.json` المولدة من العملية المنشورة أو رابط/بصمة artifact قابلة للمراجعة.
3. جدول لكل بند أعلاه: **مؤكد كما هو / مختلف**، والمسار والطريقة والصلاحية وطلب/استجابة منقحان وأكواد الخطأ.
4. إجابات صريحة عن النقاط غير الممثلة جيداً في OpenAPI: بث SSE، حفظ الاستشهادات، الإرسال الغامض، idempotency، MIME/limits، وحالات الفهرسة.
5. نتائج اختبارات القبول أدناه، مع أوامر أو تقارير قابلة لإعادة التحقق ومن دون رموز وصول أو بيانات شخصية.

الرد على وثيقة مقترحة أو فرع غير مدمج لا يُعد تأكيداً للبيئة العاملة. أي تغيير مطلوب في الباك إند يبقى من مسؤولية مالكه ولا ينفذه فريق Android.

## معايير التحقق والقبول

لا يعتمد Android الربط الحي حتى يقدم الرد دليلاً على الآتي:

1. **الإتاحة والصلاحيات:** حساب مصرح يرى مفتاح Data Search ويستطيع فتح الرحلة؛ حساب بلا الصلاحية يحصل على سلوك 403/إخفاء موثق؛ الرمز الغائب/المنتهي يعطي 401 دون تسريب بيانات.
2. **عزل المساحات:** باستخدام مساحتين وملفات/محادثات مختلفة، لا تعيد أي قائمة أو رسالة أو pin أو استرجاع بيانات المساحة الأخرى.
3. **دورة المحادثة:** إنشاء، قائمة، فتح، إعادة تسمية، حذف، ثم تأكيد أن ملفات المساحة لم تتغير. تكرار نتيجة مبهمة لا ينشئ محادثتين.
4. **السجل والصفحات:** أكثر من صفحة رسائل تعاد بترتيب `seq` ثابت؛ تحميل الأقدم لا يكرر عنصراً ولا يقدّم صفحة جزئية على أنها السجل الكامل.
5. **البث والمصالحة:** إرسال واحد ينتج waiting ثم token(s) ثم `final` أو `error`. قطع العميل بعد قبول الطلب ثم قراءة السجل يحدد بصورة قاطعة هل حُفظت الرسالة والجواب ولا يكرر الإرسال.
6. **الاستشهادات:** جواب RAG يعيد citation منظمة، ثم يعيد فتح المحادثة وتظهر البيانات نفسها من السجل؛ القيم الغائبة ممثلة طبقاً للعقد ولا يُخمن Android score أو page.
7. **النموذج:** كتالوج منشور، تثبيت capability متاحة، العودة إلى الافتراضي، ورفض قيمة مجهولة بأثر موثق دون حذف المحادثة.
8. **الرفع:** ملف مدعوم يمر بالتسجيل والرفع والإكمال؛ الرابط المنتهي، النوع غير المدعوم، الحجم الزائد وquarantine تعطي حالات وأكواداً موثقة. يختبر `text/plain` صراحة إن كان مدعوماً.
9. **الفهرسة:** الملف ready يبقى غير searchable قبل الفهرسة، ثم يمر بحالات الفهرسة حتى indexed أو failed، وتسمح قراءة موثقة بالمصالحة بعد انقطاع العميل.
10. **نطاق الاسترجاع:** بلا pins يبحث داخل كامل corpus المفهرس للمساحة؛ مع pin يبحث في المثبت فقط؛ فك آخر pin يعيد الكل؛ cross-space pin مرفوض.
11. **idempotency:** تكرار نفس المفتاح والجسم لا يكرر الأثر؛ إعادة المفتاح بجسم مختلف ترفض بعقد موثق؛ والعمليات غير المدعومة لها خطة مصالحة مثبتة.
12. **الأخطاء والتتبع:** كل فشل API يعيد RFC 9457 المنقح مع `code` و`correlation_id`، ويمكن ربطه بالسجل من دون كشف أسرار.

## أثر الانتظار على Android

يمكن مواصلة بناء واجهات Compose والحالات والاختبارات بعينات حتمية مستقلة عن الشبكة. تبقى الأمور التالية محجوبة حتى يصل رد مطابق ويُراجع:

- تفعيل بطاقة Data Search أو إضافة رحلة مستخدم قابلة للوصول إلى بيانات حقيقية.
- إنشاء Retrofit/OkHttp DTOs أو MockWebServer fixtures مبنية على مسارات أو مخططات غير مؤكدة.
- إرسال رسالة أو رفع/فهرسة/تثبيت/حذف أي مورد حقيقي.
- ادعاء نجاح تكامل أو تحقق end-to-end.
