# رحلات وتجربة Data Search Agent — تحديث العقد

الحالة: تسليم UX محدث لمرحلة `design` — قابل للمراجعة وغير معتمد للتنفيذ  
التاريخ: 2026-11-06  
المهمة: `data-search-agent`

## 1. سلطة المصادر وحدود هذا التحديث

المرجع المنتج الحاكم هو `docs/product/V1-AGREED-SCOPE.md`: إدارة المساحات وإنشاؤها مؤجلان، ووظائف Data Search لا تُعرض كجاهزة قبل إثبات الباك إند. أما تفاصيل الملفات والمعرفة أدناه فمأخوذة من حزمة `docs/api` المنسوخة من:

- الفرع: `chore/public-file-links-closing`
- الالتزام: `ff547ad8228741a532077b8eaf8fa2eb928be782`
- تاريخ الحزمة: 2026-10-22

هذه **لقطة عقد مرشحة وليست عقد `master` المؤكد**. وفق `AGENTS.md`، الباك إند العامل على `master` ولا يجوز لهذا المشروع تعديله أو الاعتماد على فرع غير مدمج. لذلك يصلح هذا التصميم للمراجعة، لكن التنفيذ والتكامل محجوبان حتى يؤكد مالك الباك إند أن المسارات والحقول والصلاحيات نفسها موجودة على `master` أو يرسل رداً موثقاً.

يعرض التطبيق حالياً بطاقة Data Search كـ«متاح لاحقاً» وغير قابلة للنقر. تظل كذلك حتى تتطابق هوية الوكيل مع عنصر مؤكد من `AgentOut` وتتوفر قدراته وصلاحياته المطلوبة. لا يوجد في `AgentOut` علم `available`؛ لا يجوز اختراع واحد.

## 2. النطاق المصمم

- اختيار **مساحة موجودة** قبل أي ملفات أو مستندات أو بحث.
- إضافة ملف عبر منتقي Android، أو تحويل نص يدخله المستخدم إلى ملف UTF-8 من نوع `text/plain` ثم تمريره في مسار الملف نفسه.
- فصل سلامة الرفع (`FileOut`) عن الفهرسة (`DocumentOut`).
- مكتبة موحدة تدمج الملف والمستند بواسطة `file_id`، مع ترقيم cursor مستقل للقائمتين.
- بحث top-k داخل مساحة واحدة، ونتائج مقتطفات مرتبطة بالمصدر.
- حذف ملف مع فهم أنه حذف ناعم للملف وتطهير غير قابل للتراجع لفهرسه.
- تحذير قبل استبدال ملف حي أقدم يحمل الاسم نفسه عند اكتشافه من العميل.

خارج النطاق: إنشاء/تعديل/حذف المساحات، المحادثة والبث، إجابة مولدة، reindex والملخصات، إدارة المنصة، تعديل الباك إند، أو الادعاء بأن لقطة الفرع منشورة.

## 4. بنية المعلومات

```text
الرئيسة
└── Data Search (بعد تحقق الكتالوج والقدرات والصلاحيات)
    ├── SCR-DS-009 اختيار مساحة موجودة / لا توجد مساحة
    └── SCR-DS-001 لوحة Data Search للمساحة المحددة
        ├── SCR-DS-002 إضافة نص كملف UTF-8
        ├── منتقي ملفات Android النظامي
        │   └── SCR-DS-010 تحذير استبدال اسم مطابق
        ├── SCR-DS-003 مكتبة المصادر (دمج files + documents)
        │   ├── SCR-DS-004 تفاصيل المصدر وحالتي السلامة/الفهرسة
        │   └── SCR-DS-008 تأكيد حذف المصدر
        └── SCR-DS-005 البحث
            ├── SCR-DS-006 نتائج top-k
            └── SCR-DS-007 مقتطف ومرجعه
```

المساحة سياق ظاهر دائماً في رأس الوكيل. تغييرها يعيد تحميل المكتبة ويمسح استعلام/نتائج المساحة السابقة؛ لا يمكن نقل ملف بين المساحات.

## 5. التنقل والرجوع والتكيف

### compact أقل من 600dp

- البطاقة المفعلة ← `SCR-DS-009` عند عدم وجود اختيار صالح، وإلا `SCR-DS-001` مع شريحة مساحة واضحة قابلة للتغيير.
- Back من اختيار المساحة يعود للرئيسة؛ Back من اللوحة يعود للرئيسة؛ من النتائج يعود للبحث مع الاستعلام؛ ومن التفاصيل يعود للقائمة مع موضعها.
- إضافة نص شاشة كاملة. اختيار ملف يستخدم منتقي Android. الحوارات تغلق قبل مغادرة الشاشة.
- تغيير المساحة مع عملية محلية غير مكتملة يطلب الإلغاء أو البقاء؛ لا ينسب العملية لمساحة أخرى.

### expanded 600dp فأكثر

- rail العام يبقى كما هو. اختيار المساحة يظهر كلوحة/حوار واضح قبل المحتوى.
- تستخدم المكتبة/النتائج قائمتين: قائمة أولية وتفصيل نهائي. عند `fontScale >= 1.3` أو ضيق الارتفاع تعود للوحة واحدة.
- لا تُعرض بيانات من مساحتين معاً؛ تبديل المساحة يفرغ اللوحتين قبل الجلب.

### الروابط والاستعادة

- لا رابط عميق قبل تثبيت key الوكيل ومعرفات المساحات/المصادر على `master`.
- بعد موت العملية تحفظ الواجهة، مع عزل الحساب والمساحة: operation id، `Idempotency-Key`، `file_id` بعد التسجيل، و`document_id` بعد 202. عند الاستعادة تستعلم عن الحالة ولا تعيد POST/PUT عمياء.
- presigned URL مؤقت؛ انتهاءه يحتاج سياسة backend مؤكدة. التصميم يعرض «انتهت مهلة الرفع» ولا يولد تسجيلاً جديداً تلقائياً قبل المصالحة.
- cache ليس تفويضاً. عند انتهاء الجلسة/رفض الصلاحية يحجب كل اسم ملف ومقتطف محفوظ فوراً.

## 6. الرحلات

### J-DS-01 — التحقق من الوكيل والدخول

**المتطلبات:** DS-REQ-01، 09، 13

1. يجلب التطبيق كتالوج الوكلاء.
2. يطابق Data Search بمفتاح/قدرة يؤكدها العقد، لا بالاسم المرئي وحده.
3. يقرأ `capabilities` و`required_permissions` ويقارنها بسياق صلاحيات المستخدم المؤكد.
4. عنصر مفقود أو قدرة غير مؤكدة: البطاقة «متاح لاحقاً» وغير قابلة للنقر.
5. عنصر معروف مع نقص صلاحية: البطاقة/الدخول يشرح عدم توفر الوصول دون كشف مصادر أو أسماء.
6. عند الاستيفاء يفتح اختيار المساحة أو اللوحة.

**مانع تنفيذ:** لا توثق اللقطة key/capability التي تعرّف Data Search ولا مصدر صلاحيات العميل على `master`.

### J-DS-02 — اختيار مساحة موجودة

**المتطلبات:** DS-REQ-02، 03، 13

1. تعرض `SCR-DS-009` قائمة `GET /spaces` وتتابع cursor حتى النهاية عند البحث عن الاختيار أو أثناء التمرير.
2. إن بقيت مساحة واحدة يمكن تحديدها تلقائياً مع إظهار اسمها؛ أكثر من واحدة تتطلب اختياراً صريحاً أو آخر اختيار ما زال صالحاً.
3. لا يوجد زر إنشاء/تعديل/حذف.
4. لا توجد مساحة: حالة مانعة «لا توجد مساحة متاحة» مع رجوع للرئيسة/تحديث، دون استخدام UUID ثابت أو إنشاء ضمني.
5. الاختيار يرافق كل listFiles/listDocuments/search/register. تغيير المساحة يفرغ البيانات السابقة أولاً.

### J-DS-03 — إضافة ملف وفهرسته

**المتطلبات:** DS-REQ-03..05، 09، 10، 12

1. يتطلب مساحة وصلاحية ملفات للكتابة و`knowledge:manage` للفهرسة. إن توفرت الكتابة فقط، يمكن رفع الملف لكن يجب أن توضح الواجهة أنه لن يُفهرس حتى يملك المستخدم إدارة المعرفة؛ المنتج يقرر إن كان يسمح بهذا الفصل.
2. يفتح منتقي Android. الإلغاء يعود بلا خطأ ولا إذن تخزين عام.
3. يقرأ العميل الاسم وMIME والحجم. القبول الفعلي للـMIME والحدود يحتاج تأكيد `master`.
4. يفحص كل صفحات ملفات المساحة بحثاً عن اسم حي مطابق وفق lower(NFC). إن وجد يفتح `SCR-DS-010` قبل التسجيل؛ الإلغاء لا يرفع شيئاً.
5. `POST /files` بجسد `space_id/name/content_type/size_bytes` و`Idempotency-Key` ثابت للعملية؛ يحصل على `file_id/upload_url/expires_in`.
6. PUT للبايتات إلى الرابط الموقع، ثم `POST /files/{id}/complete`.
7. نتيجة complete قد تستبدل ملفاً أقدم مطابق الاسم وتطهر فهرسه. فحص العميل تحذير best-effort فقط؛ ملف متزامن قد يصنع تصادماً بعد الفحص.
8. تعرض حالة سلامة منفصلة: `uploaded` ثم `scanning` ثم `ready` أو `quarantined`. المحجور لا يفهرس ولا يظهر كفشل indexing.
9. عند `ready` فقط: `POST /knowledge/documents` بـ`file_id` و`Idempotency-Key` آخر ثابت. 202 يعيد مستنداً `pending`.
10. تعرض حالة فهرسة منفصلة: `pending` ← `indexing` ← `indexed` أو `failed`. لا يظهر المصدر في البحث قبل `indexed`.

**فشل جزئي:** ready بلا document = «الملف آمن وجاهز؛ لم تبدأ الفهرسة». `failed` = «فشلت الفهرسة» بلا سبب خام لأن `DocumentOut` لا ينشر error.  
**موت العملية:** يصالح `file_id`/`document_id`; لا يعيد التسجيل أو الفهرسة بمفتاح جديد.  
**quarantined:** رسالة أمان محايدة ومسار حذف/رجوع وفق الصلاحية، دون محاولة index.

### J-DS-04 — إضافة نص عبر مسار الملف

**المتطلبات:** DS-REQ-03..06، 09، 10، 12

1. يدخل المستخدم عنواناً وcontent في `SCR-DS-002`.
2. ينشئ Android تمثيلاً مؤقتاً UTF-8 باسم ظاهر وMIME `text/plain`، ويحسب size_bytes الفعلي.
3. يمر الاسم على فحص التصادم والتحذير نفسه.
4. ينفذ رحلة الملف كاملة؛ لا POST نص خاص.
5. تمسح النسخة المؤقتة/المسودة حسب سياسة محلية معزولة عند النجاح أو الخروج؛ سياسة الاحتفاظ بعد موت العملية تحتاج اعتماداً أمنياً.

**مانع:** قبول `text/plain` وحدود النص والاسم الافتراضي غير مؤكدة على `master`.

### J-DS-05 — مكتبة موحدة

**المتطلبات:** DS-REQ-03، 05، 07، 09، 11، 13

1. يجلب التطبيق `GET /files?space_id=...` و`GET /knowledge/documents?space_id=...`، ولكل قائمة cursor مستقل.
2. يدمج `DocumentOut.file_id` مع `FileOut.id`. لا يربط بالاسم.
3. صف الملف يعرض خط سلامة وخط فهرسة منفصلين:
   - `scanning` + لا مستند: «فحص أمان جارٍ / الفهرسة لم تبدأ».
   - `ready` + لا مستند: «جاهز / غير مفهرس».
   - `ready` + `pending|indexing`: «جاهز / الفهرسة قيد التنفيذ».
   - `ready` + `indexed`: «جاهز / قابل للبحث».
   - `quarantined`: «محجور / غير قابل للفهرسة».
   - `failed`: «آمن / فشلت الفهرسة».
4. اختلاف سرعة الصفحتين لا يسبب حالة خاطئة؛ يعرض «جارٍ جلب حالة الفهرسة» إلى أن تعرف صفحة المستندات ذات الصلة أو تكتمل.
5. لا يقال «كل المصادر» حتى يصل `next_cursor=null` في القائمتين.

### J-DS-06 — البحث وقراءة النتيجة

**المتطلبات:** DS-REQ-03، 08، 09، 10، 13

1. يتطلب مساحة و`knowledge:read` ومصدراً واحداً `indexed` على الأقل.
2. يرسل `POST /knowledge/search` مع query وspace_id وk. التصميم يبدأ بالافتراضي 5.
3. البحث top-k فقط؛ لا cursor ولا infinite scroll. أي «إظهار المزيد» يعيد طلباً بـk أكبر حتى 50 فقط بعد قرار منتج واضح.
4. تعرض كل نتيجة `text` و`file_name` إن وجد، ثم `page_number` و`section` إن لم يكونا null.
5. لا تعرض `score` للمستخدم افتراضياً؛ يحتاج معنى/عتبة وقرار منتج. لا تصاغ إجابة مولدة.
6. النتيجة بلا اسم/صفحة/قسم تعرض تسمية مصدر عامة ولا تخترع metadata.

### J-DS-07 — حذف ملف وفهرسه

**المتطلبات:** DS-REQ-09، 11

1. يظهر الإجراء فقط عند صلاحية الحذف الفعلية للملفات؛ `knowledge:manage` وحدها لا يفترض أنها تكفي.
2. `SCR-DS-008` يذكر: لا تراجع؛ سيختفي الملف من القراءة وسيُطهّر فهرسه ومستنداته ونتائجه.
3. التأكيد يرسل `DELETE /files/{id}`. يبقى الصف «جارٍ الحذف» حتى 204.
4. فشل/نتيجة مجهولة يصالح GET/list قبل retry، ولا يعلن الحذف مبكراً.

## 7. مصفوفة الصلاحيات

| القدرة الفعلية | تجربة الواجهة |
|---|---|
| كتالوج بلا عنصر/قدرة Data Search مؤكدة | بطاقة «متاح لاحقاً»، غير تفاعلية |
| نقص أي `required_permissions` للوكيل | دخول مرفوض آمن؛ لا cache ولا أسماء |
| `knowledge:read` فقط | اختيار مساحة، قراءة حالات المستندات والبحث؛ لا index/retry مكلف |
| `knowledge:manage` بلا `knowledge:read` | لا تفترض صلاحية القراءة؛ أفعال الإدارة تظهر فقط إن سمح سياق endpoint، ولا تعرض corpus |
| صلاحية ملفات القراءة دون الكتابة | مكتبة الملفات المصرح بها؛ إضافة النص/الملف معطلة مع سبب |
| صلاحية ملفات الكتابة دون `knowledge:manage` | الرفع فقط قرار منتج صريح؛ لا يوصف كمصدر قابل للبحث |
| نقص صلاحية حذف الملف | حذف مخفي/معطل، لا محاولة متفائلة |
| 403 أثناء أي عملية | امسح المحتوى الحساس المتأثر واعرض رفضاً، ولا تستنتج وجود مورد |

أسماء صلاحيات قراءة/حذف الملفات الدقيقة غير موثقة في المقاطع المقروءة؛ يجب أخذها من سياق الحساب/`required_permissions` المؤكد على `master`، لا تخمينها.

## 8. الحالات المشتركة

| الحالة | العرض | المخرج |
|---|---|---|
| Loading | عنوان وسياق المساحة ثابتان + إعلان واحد | Back متاح |
| No space | لا محتوى/بحث/رفع | تحديث أو رجوع؛ بلا إنشاء |
| Empty | لا ملفات في المساحة | إضافة إن سمحت الصلاحية |
| Uploading | خطوة «رفع البايتات» مستقلة | لا index حتى complete/ready |
| Scanning | سلامة الملف قيد الفحص | مراقبة/رجوع |
| Quarantined | محجور، غير قابل للفهرسة | حذف/رجوع وفق الصلاحية |
| Pending/indexing | الفهرسة قيد التنفيذ | مراقبة؛ البحث معطل لهذا الملف |
| Indexed | قابل للبحث | بحث/فتح التفاصيل |
| Failed | فشل الفهرسة بلا raw error | retry فقط بعقد وصلاحية |
| Partial | يحتفظ بالحالة المؤكدة ويميز المجهول | مصالحة الجزء المتأثر |
| Offline | لا رفع ولا index ولا بحث جديد | retry عند الاتصال؛ cache ليس تفويضاً |
| Permission denied | يحجب البيانات التي لم تعد مصرحاً بها | رجوع/تحديث الصلاحيات |
| Session expired | يحجب كل محتوى الحساب | تسجيل الدخول |
| Destructive | أثر دقيق + إلغاء افتراضي | إلغاء/تأكيد صريح |

## 9. الوصول والتوطين

- كل هدف تفاعلي 48×48dp. العناوين headings، والحقول labels ثابتة.
- قارئ الشاشة يعلن خطي سلامة الملف والفهرسة منفصلين، ولا يكرر الأيقونة.
- تغير الحالة المهم فقط live announcement؛ polling لا يزعج بإعلانات متكررة.
- RTL يعكس back/start/end؛ أسماء الملفات وUUID تبقى باتجاهها الطبيعي. الصفحة/القسم نصان مترجمان.
- font scale 1.3 و2.0: صف الحالة يتحول لعمود ولا يقتطع اسم الملف أو الأثر الهدام.
- الخطأ ليس لوناً فقط. score غير معروض، ولا تعتمد دلالة نتيجة البحث على ترتيب بلا تسمية.
- offline لا يعرض مقتطفات حساسة مخزنة إلا إذا اعتمدت سياسة لاحقة مع عزل الحساب/المساحة؛ الافتراضي الآمن هو الحجب.

## 10. التعارضات والمانعات الدقيقة قبل التنفيذ

1. V1 يؤجل إنشاء وإدارة المساحات، بينما كل تسجيل/سرد ملف، سرد مستند، وبحث يحتاج `space_id`. الحل التصميمي اختيار مساحة موجودة فقط؛ الحساب بلا مساحة **محجوب وظيفياً** ولا يجوز علاجه ضمن Android.
2. لقطة العقد من فرع `chore/public-file-links-closing` وليست `master`. يجب تأكيد المسارات/DTO/status/idempotency/collision/delete على `master`.
3. key/capability التي تعرّف Data Search، ومصدر قائمة صلاحيات المستخدم، وأسماء صلاحيات الملفات الدقيقة غير مثبتة.
4. MIME والأحجام والحصة المقبولة على `master`، ولا سيما `text/plain`، تحتاج تأكيداً.
5. لا حماية ذرية موثقة تمنع سباق الاسم بين فحص العميل وcomplete؛ التحذير best-effort ولا يلغي الخطر.
6. استعادة upload URL منتهي، وسياسة retry لـcomplete بنتيجة مجهولة، تحتاج عقداً مؤكداً.
7. `DocumentOut` لا يحمل سبب failure؛ لا يمكن تصميم رسالة تفصيلية صادقة.
8. لا cursor للبحث؛ سلوك «المزيد» يحتاج قرار منتج أو يبقى k=5.

لا يتطلب هذا التحديث تعديل باك إند. إن قرر التنفيذ قبل دمج العقد، يجب على director/liaison إنشاء طلب Backend منفصل والانتظار لرد موثق.
