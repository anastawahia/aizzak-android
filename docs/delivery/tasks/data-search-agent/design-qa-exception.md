## المخاطر والحدود المنقولة إلى القبول

1. اختلاف سياق وأيقونات حوارات الحذف، وهوية المساعد والبطاقات وأدوار الألوان والتسلسل البصري للرفع عن التصميم المعتمد.
2. ظهور تعليمات عقد تنفيذية في حوار حذف المصدر؛ يُعرض ذلك كقيد معروف في الشريحة الحالية.
3. غياب بعض أدلة الحالات الفارغة/المحجوبة/الأخطاء؛ لا يعني غياب تنفيذها البرمجي، لكنه يمنع إثبات المطابقة البصرية لها.
4. ملاحظة P3 عن selected semantics للمحادثة المختارة، وعدم تنفيذ اختبارات جهاز/TalkBack/IME.
5. الشريحة stateless وغير مربوطة بـHome أو التنقل أو الشبكة. قبول الواجهات لا يثبت جاهزية المنتج التشغيلي أو التكامل الحي.

## نطاق الاستثناء

يسمح القرار بالانتقال إلى مراجعة حزمة القبول دون إعادة إصلاح. لا يثبت مطابقة التصميم، ولا يُسجل اعتماداً منفصلاً لكل عنصر منحرف، ولا قبولاً نهائياً للتطبيق، ولا تفويضاً للنشر أو لتعديل الباك إند أو لتفعيل مسارات غير مؤكدة.

## تمثيل الحالة

أداة lifecycle الحالية لا تملك حالة `waived/failed-with-owner-exception`؛ وهي تشترط تقرير design-qa ناجحاً لتمرير القبول آلياً. لذلك حُفظ الاستثناء هنا، وحُضرت [حزمة القبول](acceptance-packet.md) بمسار يدوي موثق. بقي سجل الأداة صادقاً: verification passed،design-qa pending مع تقرير فاشل،acceptance pending،completed=false. لم تُعدل الأداة أو شروطها أو lifecycle يدوياً.

الحالة التشغيلية للمهمة موضحة في [status.md](status.md). أي قبول لاحق يُربط بحزمة القبول وبصمة المصدر والقيود أعلاه، ويُسجل كقرار يدوي إذا بقي قيد الأداة.
