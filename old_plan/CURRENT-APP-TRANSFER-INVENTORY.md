> الغرض من هذه الوثيقة: أن تكون مدخلاً عملياً لكتابة وثيقة متطلبات المنتج والتطبيق الجديد، بالاعتماد عليها مع وثائق الـAPI الموجودة في `C:\Users\anast\Desktop\api-documents`.
>
> مصدر التحليل: تطبيق Expo الحالي في `C:\Users\anast\Desktop\ai-assistant\android`، وحالة الكود بتاريخ 2026-10-30.

## 1. الخلاصة التنفيذية

يجب الحفاظ على تجربة التطبيق الحالي وهويته البصرية الأساسية، لكن لا ينبغي نسخ بنيته الوظيفية أو طبقة البيانات حرفياً. التطبيق الحالي مبني حول كيان واحد اسمه **Agent** ينشئه المستخدم ويضع الرسائل تحته، أما الباك اند الجديد فيستخدم التسلسل التالي:

`Space → Agent من كتالوج المنصة → Conversation → Messages`

لذلك تكون قاعدة النقل كما يلي:

- ننقل الهوية البصرية، رحلة المصادقة، سهولة بدء المحادثة، واجهة الدردشة، الإعدادات ثنائية اللغة، حالات التحميل والفراغ، وبعض خصائص العمل دون اتصال.
- نعيد صياغة شاشة الوكلاء القديمة لتصبح تجربة مبنية على المساحات والمحادثات والوكلاء المتاحين من الكتالوج.
- لا ننقل مسارات الـAPI القديمة، معرفات الأرقام الصحيحة، قائمة النماذج الثابتة، أو قائمة المزامنة القديمة.
- الميزات التي لا يدعمها عقد الـAPI الجديد بوضوح، مثل تعديل صورة الحساب والاسم وحذف الحساب ذاتياً، تبقى متطلبات معلقة ولا تُنفذ بالافتراض.

## 4. رحلة المصادقة والحساب

### 4.1 خصائص موجودة يجب الحفاظ عليها

| الخاصية الحالية | التصنيف | الصياغة المطلوبة في التطبيق الجديد |
|---|---|---|
| إنشاء حساب بالبريد وكلمة المرور | نقل مباشر | يبقى عبر Firebase Authentication. |
| تسجيل الدخول | نقل مباشر | بعد نجاح Firebase يُرسل ID Token في `Authorization: Bearer ...` إلى كل طلب محمي. |
| إظهار/إخفاء كلمة المرور | نقل مباشر | الحفاظ على السلوك في حقول الدخول والتسجيل وتغيير كلمة المرور. |
| التحقق من البريد | معلّق | الحفاظ عليه إذا كانت سياسة المنتج/الباك اند تشترط `emailVerified`؛ وثائق الـAPI لا تحسم هذا الشرط. |
| إعادة إرسال رسالة التحقق مع مهلة 60 ثانية | نقل مباشر بعد حسم السياسة | تجربة جيدة لمنع التكرار، ويمكن إبقاؤها إن بقي التحقق مطلوباً. |
| استعادة كلمة المرور بالبريد | نقل مباشر | تتم عبر Firebase. |
| تغيير كلمة المرور بعد إعادة التحقق | نقل مباشر | تتم عبر Firebase مع reauthentication. |
| تسجيل الخروج | نقل مع تكييف | تنفيذ تسجيل خروج Firebase، واستدعاء `/me/logout` إذا كانت الجلسة الخلفية تتطلب ذلك، ثم مسح بيانات الحساب الحساسة محلياً. |
| إنشاء المستخدم في الباك اند | نقل مع تكييف | لا يُستدعى `/users/` القديم؛ الباك اند الجديد ينشئ/يحدّث المستخدم JIT من Firebase token ثم يعيد السياق من `/me/context`. |
| نبضة الحضور | نقل مع تكييف | استخدام `/me/heartbeat` عند بدء الجلسة، أثناء النشاط، وعند عودة التطبيق للمقدمة. |

### 4.2 بيانات الحساب الموجودة حالياً

واجهة الحساب الحالية تعرض:

- صورة المستخدم أو الحرف الأول من الاسم/البريد.
- اسم المستخدم.
- البريد الإلكتروني وحالة التحقق.
- دور المستخدم أو المدير.
- تاريخ إنشاء الحساب.
- تعديل الاسم.
- تعديل الصورة من معرض الصور.
- تغيير كلمة المرور.
- تسجيل الخروج.
- حذف الحساب نهائياً لغير المدير.

### 4.3 عناصر حساب معلقة بسبب نقص عقد الـAPI

وثائق الـAPI الجديدة لا توفر للمستخدم العادي عقداً واضحاً للآتي:

- قراءة ملف شخصي كامل يحتوي البريد واسم العرض والصورة وتاريخ الإنشاء؛ `/me/context` يعيد حالياً معرف المستخدم والمساحة والأدوار والصلاحيات فقط.
- تعديل اسم العرض/اسم المستخدم.
- رفع أو تعديل صورة الحساب.
- حذف المستخدم لحسابه ذاتياً وحذف بياناته التابعة.

هذه العناصر يجب أن تظهر في وثيقة المتطلبات كفجوات Backend، لا أن يُفترض لها endpoint غير موثق.

### 4.4 منطق قديم لا يُنقل

- حذف حساب Firebase غير المفعّل تلقائياً من التطبيق بعد عشر دقائق.
- إرسال `firebase_uid` و`email` يدوياً إلى `/users/` دون Bearer token.
- حفظ نسخة طويلة العمر من سجل المستخدم الخلفي واستخدامها كحقيقة نهائية عند تغير الصلاحيات.

## 5. الصفحة الرئيسية ونموذج الاستخدام

### 5.1 التجربة المهمة في التطبيق الحالي

الشاشة الحالية توفر:

- تحية شخصية باسم المستخدم.
- قائمة بطاقات سهلة الفهم.
- عدد العناصر وتاريخ الإنشاء والنموذج المستخدم.
- سحب للتحديث.
- حالة تحميل وحالة فراغ مصورة.
- زر عائم لإنشاء عنصر جديد.
- إنشاء، إعادة تسمية، حذف، وفتح المحادثة.
- اقتراحات أسماء سريعة عند الإنشاء.
- تأكيد قبل الحذف وتحذير بأن البيانات التابعة ستُحذف.

هذه مبادئ تجربة جيدة يجب الحفاظ عليها، لكن ليس على كيان Agent القديم.

### 5.2 التحويل المطلوب إلى نموذج الباك اند الجديد

**التصنيف: نقل مع تكييف جوهري.**

| في التطبيق الحالي | في التطبيق الجديد |
|---|---|
| المستخدم ينشئ Agent باسمه ونموذجه | المستخدم يختار Space، ثم Agent من كتالوج `/agents`، ثم ينشئ Conversation اختيارياً بعنوان. |
| قائمة الوكلاء هي الصفحة الرئيسية | الصفحة الرئيسية تعرض Spaces، وآخر Conversations أو اختصاراً لبدء محادثة. |
| إعادة تسمية Agent | إعادة تسمية Space أو Conversation حسب مكان الإجراء. |
| حذف Agent يحذف محادثاته | حذف Conversation يحذف الخيط، وحذف Space عملية أكبر تحذف كل محتواه ويجب أن تحمل تحذيراً أقوى. |
| نموذج واحد محفوظ داخل Agent | النموذج يثبت على Conversation بواسطة route قادم من `/models`. |
| agent id رقمي | `agent_key` نصي من الكتالوج، بينما Space وConversation وMessage تستخدم UUID. |

### 5.3 تجربة مقترحة لبدء محادثة جديدة

للحفاظ على بساطة التطبيق الحالي:

1. يضغط المستخدم «محادثة جديدة».
2. يختار Space، أو ينشئ Space إن لم يوجد.
3. يختار Agent من قائمة ديناميكية تعرض الاسم والوصف والقدرات.
4. يكتب عنواناً اختيارياً للمحادثة.
5. يختار نموذجاً اختيارياً من `/models` أو يترك اختيار الوكيل الافتراضي.
6. تُنشأ Conversation ثم تفتح شاشة الدردشة.

يجب أن تدعم حالة المستخدم الجديد مساراً موجهاً لإنشاء أول Space ثم أول Conversation دون كشف التعقيد الداخلي دفعة واحدة.

## 6. شاشة المحادثة

### 6.1 خصائص واجهة يجب نقلها

**التصنيف: نقل مباشر في تجربة الاستخدام، مع إعادة تنفيذ البيانات.**

- عنوان المحادثة واسم/نوع الوكيل في الرأس.
- عرض رسائل المستخدم والمساعد بشكلين بصريين مختلفين.
- صورة المستخدم أو الحرف الأول، وصورة المساعد.
- عرض ردود المساعد بصيغة Markdown، بما فيها العناوين والقوائم والروابط ومقاطع الكود والاقتباسات.
- عرض وقت الرسالة.
- نسخ محتوى الرسالة مع مؤشر نجاح مؤقت.
- حذف رسالة بعد تأكيد المستخدم.
- مؤشر كتابة متحرك أثناء انتظار الرد.
- زر عائم للعودة إلى آخر الرسائل عندما يبتعد المستخدم عن الأسفل.
- مربع كتابة متعدد الأسطر وزر إرسال واضح.
- منع الإرسال الفارغ والإرسال المتكرر أثناء الطلب.
- عداد أحرف قرب الحد؛ الحد الحالي 4000، ويجب تثبيت حد جديد في عقد المنتج والـAPI قبل اعتماده.
- اقتراحات سريعة عندما تكون المحادثة فارغة، بالعربية والإنجليزية.
- قائمة إجراءات للمحادثة.
- اختيار نموذج المحادثة.
- حالة فراغ مصورة ومفيدة.

### 6.2 خصائص جديدة يفرضها الباك اند الجديد

- دعم `content` ككائن منظم، وليس افتراض أنه نص عادي دائماً.
- دعم أدوار الرسائل: `user`, `assistant`, `system`, `tool`.
- استخدام ترتيب `seq` بدلاً من الاعتماد على رقم المعرف.
- دعم pagination/cursor عند جلب الرسائل القديمة.
- عرض `token_count` أو بيانات `usage` بصياغة واضحة.
- دعم streaming عبر SSE في المرحلة الأولى، ثم WebSocket إذا كانت التفاعلية والإلغاء والإشعارات مطلوبة.
- عرض حدث `notice`، خصوصاً انتقال النموذج إلى fallback، دون خلطه برسالة المستخدم.
- إظهار tool calls بشكل مبسط أو قابل للطي.
- إظهار citations لوكيل RAG، بما فيها اسم الملف والصفحة والترتيب.
- معالجة أخطاء RFC 9457 وإظهار رسالة مناسبة مع `correlation_id` عند الحاجة للدعم.
- دعم إعادة الاتصال وتحديث الحالة بعد إغلاق WebSocket بالرمز 1013.

### 6.3 إجراءات المحادثة وتوافق الـAPI

| الإجراء | دعم الـAPI الجديد | القرار المطلوب |
|---|---|---|
| إنشاء محادثة | مدعوم | مطلوب في الإصدار الأول. |
| تغيير عنوان المحادثة | مدعوم | ينقل وظيفة إعادة التسمية القديمة إلى Conversation. |
| حذف المحادثة | مدعوم | مطلوب مع تأكيد. |
| حذف رسالة واحدة | مدعوم | مطلوب، مع المسار المتداخل داخل Conversation. |
| مسح جميع الرسائل مع إبقاء المحادثة | لا يوجد endpoint جماعي واضح | يفضل حذف المحادثة وبدء أخرى، أو إضافة API مخصص؛ لا ترسل عشرات طلبات الحذف دون قرار. |
| تغيير النموذج | مدعوم | يرسل `ModelOut.capability` في `route`، وليس اسم model خاماً. |
| إلغاء إجابة جارية | مدعوم في WebSocket | يضاف عندما تعتمد مرحلة WebSocket. |
| تثبيت ملفات للمحادثة | مدعوم | ميزة جديدة مهمة لوكيل RAG. |

### 6.4 عداد الرموز

التطبيق الحالي يجمع `tokens_used` لكل الرسائل المعروضة. في التطبيق الجديد توجد pagination وقد لا تكون كل الرسائل محملة؛ لذلك يجب ألا تعرض الواجهة مجموعاً على أنه إجمالي كامل إلا إذا كان الباك اند يعيده صراحة. الخيارات:

- عرض استهلاك آخر إجابة فقط.
- عرض مجموع الرسائل المحملة مع تسمية واضحة.
- استخدام `/usage` لعرض استهلاك موثوق في شاشة منفصلة.

## 7. العمل دون اتصال والتخزين المحلي

### 7.1 ما يجب الحفاظ عليه

- مراقبة اتصال الشبكة.
- شريط واضح عند انقطاع الاتصال.
- فتح البيانات التي سبق تحميلها من cache عند عدم توفر الشبكة.
- الاحتفاظ بمسودة الرسالة محلياً.
- حالات retry واضحة بعد فشل الطلب.
- عدم تجميد الواجهة بسبب timeout طويل أو شبكة ضعيفة.

### 7.2 ما لا يجب نسخه من التطبيق الحالي

التطبيق الحالي يضع إنشاء الوكلاء وإرسال الرسائل والحذف وتغيير النموذج في `sync_queue` ثم يعيدها تلقائياً. لا ينبغي نسخ ذلك كما هو لأن:

- إرسال الرسائل وإنشاء المحادثات لا يعلنان `Idempotency-Key` في العقد الجديد.
- إعادة الإرسال التلقائي بعد عدم معرفة نتيجة الطلب قد تنشئ رسالة أو محادثة مكررة.
- نموذج المعرفات تغير من INTEGER إلى UUID، ومحتوى الرسالة تغير من TEXT إلى JSON object.

السياسة المقترحة للإصدار الأول:

- cache للقراءة فقط لآخر Spaces وAgents وConversations وMessages.
- حفظ drafts محلياً.
- عند فشل إرسال رسالة، تبقى كمسودة/عنصر فاشل ويضغط المستخدم «إعادة المحاولة» صراحة.
- لا يُرسل الطلب تلقائياً عند عودة الاتصال ما لم يضاف للـAPI مفتاح idempotency موثق لهذه العملية.

### 7.3 نموذج تخزين جديد مطلوب

لا يعاد استخدام جداول SQLite الحالية. الحد الأدنى الجديد:

- `spaces`: معرف UUID، الاسم، العدادات، تاريخ الإنشاء.
- `agents_catalog`: المفتاح، الاسم، الوصف، القدرات، الإصدار.
- `models_catalog`: capability، provider، model، available.
- `conversations`: UUID، space ID، agent key، العنوان، model route، التاريخ.
- `messages`: UUID، conversation ID، seq، role، content JSON، token count، التاريخ، وحالة محلية عند الحاجة.
- `drafts`: conversation ID أو مفتاح إنشاء مؤقت، والنص والتاريخ.
- cursor metadata لكل قائمة paginated عند الحاجة.

|---|---|---|
| العربية والإنجليزية | نقل مباشر | يجب دعم RTL فعلياً، لا ترجمة النصوص فقط. |
| المظهر الفاتح | نقل مباشر | يعتمد لوحة الألوان الحالية. |
| المظهر الداكن | نقل مباشر | يعتمد لوحة الألوان الحالية. |
| اتباع إعداد النظام | نقل مباشر | يبقى خياراً ثالثاً. |
| حفظ الاختيارات محلياً | نقل مباشر | اللغة والثيم واختيارات UX غير الحساسة في AsyncStorage. |
| النموذج الافتراضي | نقل مع تكييف | مصدر الخيارات `/models`، وتُحفظ `capability` لا اسم النموذج الخام. |
| صفحة معلومات الإصدار | نقل مباشر | الإصدار يقرأ من إعدادات التطبيق لا من ثابت داخل الشاشة. |

### 8.2 متطلبات RTL

التطبيق الحالي يترجم النصوص لكنه لا يعكس كل التخطيطات والرموز بشكل متسق. التطبيق الجديد يجب أن يحدد في وثيقة المتطلبات:

- محاذاة النصوص والحقول والقوائم حسب اللغة.
- اتجاه أزرار الرجوع والأسهم.
- ترتيب الأيقونات والنصوص داخل الصفوف.
- تنسيق التاريخ والوقت والأرقام.
- سلوك Markdown العربي ومقاطع الكود داخل واجهة RTL.

## 9. الأدوات والتكاملات

### 9.1 ما يظهر حالياً

التطبيق الحالي يعرض أدوات ثابتة:

- الطقس.
- أسعار العملات.
- أخبار الرياضة.
- الأخبار.
- البحث عبر الإنترنت.
- الحاسبة.
- Gmail قابل للربط والفصل.

القائمة الثابتة هي عرض بصري وليست مصدراً موثوقاً لقدرات الباك اند.

### 9.2 الصياغة الجديدة المطلوبة

**التصنيف: نقل مع تكييف.**

- قدرات الوكيل تأتي من `AgentOut.capabilities`.
- الأدوات المكتشفة تأتي من `/tools` أو عقد discovered tools في الوثائق.
- الموصلات تأتي من `/integrations/connectors`.
- الاتصالات الفعلية تأتي من `/integrations/connections`.
- Gmail يصبح connector ضمن نظام integrations العام، لا endpoints خاصة بالمستخدم.
- الواجهة تعرض حالة الاتصال: pending، connected، revoked، error.
- يجب تحديد deep link أو universal/app link لعودة OAuth إلى تطبيق الهاتف؛ الوثائق الحالية لا تكفي لتحديد رحلة العودة على Android بالكامل.
- لا تُخزن tokens أو secrets في التطبيق، ولا يعرضها الباك اند أصلاً.

## 10. الإدارة والصلاحيات

### 10.1 قيمة لوحة الإدارة الحالية التي تُنقل

- قائمة المستخدمين.
- عرض الحالة online/offline.
- عرض الأدوار والحالة active/disabled.
- تعطيل أو إعادة تفعيل المستخدم.
- منح أو إزالة صلاحيات الإدارة.
- حذف المستخدم بعد تأكيد.
- بطاقات إحصائية.
- تحديث يدوي وتحديث دوري.

### 10.2 تكييفها مع الـAPI الجديد

- إظهار لوحة الإدارة بناءً على `roles` و`permissions` من `/me/context`، وليس Boolean محلياً فقط.
- إزالة الحماية المبنية على بريد مكتوب داخل التطبيق؛ الخادم هو مصدر الصلاحيات الوحيد.
- دعم pagination والبحث `q` في قائمة المستخدمين.
- استخدام الإحصاءات المعادة من API بدلاً من حساب أرقام غير مكتملة في الهاتف.
- تمييز `platform_admin` عن أدوار workspace: owner/admin/member/viewer.
- طلب سبب إداري `reason` عند التعطيل أو الحذف لأن العقد الجديد يشترطه للتدقيق.
- احترام منع تعديل المستخدم لنفسه ومنع إزالة آخر owner أو آخر platform admin حسب رد الخادم.
- يمكن لاحقاً إضافة system stats وإدارة providers؛ لم تكن موجودة في التطبيق الحالي فلا تدخل في الحد الأدنى إلا بقرار منتج.

## 11. حالات الواجهة المشتركة التي يجب الحفاظ عليها

كل شاشة قائمة أو طلب شبكة في التطبيق الجديد يجب أن تحدد الحالات التالية:

- Loading أولي.
- Refresh يدوي.
- Empty state مع نص وإجراء واضح.
- Error state قابل لإعادة المحاولة.
- Offline/cached state.
- Mutation in progress لمنع النقر المكرر.
- Success feedback قصير بعد الحفظ أو النسخ.
- Confirm dialog للعمليات المدمرة.
- Permission denied بحسب صلاحيات الخادم.
- Session expired مع محاولة تجديد Firebase token مرة واحدة ثم العودة للدخول.

## 12. متطلبات وظيفية أولية مقترحة لوثيقة المتطلبات

هذه القائمة ليست PRD نهائية، لكنها نواة قابلة للتحويل إلى قصص مستخدم ومعايير قبول.

### المصادقة

- **MOB-FR-001:** يستطيع المستخدم إنشاء حساب وتسجيل الدخول بالبريد وكلمة المرور عبر Firebase.
- **MOB-FR-002:** يرفق التطبيق Firebase ID Token بكل طلب API محمي ويجدد الرمز عند انتهاء الصلاحية.
- **MOB-FR-003:** يجلب التطبيق سياق المستخدم والمساحة والأدوار والصلاحيات من `/me/context` بعد الدخول.
- **MOB-FR-004:** يستطيع المستخدم استعادة وتغيير كلمة المرور وتسجيل الخروج.
- **MOB-FR-005:** يرسل التطبيق heartbeat أثناء الجلسة النشطة دون استهلاك زائد للبطارية.

### المساحات والكتالوج

- **MOB-FR-010:** يستطيع المستخدم عرض Spaces وإنشاءها وإعادة تسميتها وحذفها حسب الصلاحيات.
- **MOB-FR-011:** يعرض التطبيق تحذيراً واضحاً بأن حذف Space يحذف الملفات والمستندات والمحادثات التابعة نهائياً.
- **MOB-FR-012:** يستطيع المستخدم عرض Agents المتاحين مع الوصف والقدرات والصلاحيات المطلوبة.
- **MOB-FR-013:** يستطيع المستخدم عرض Models المتاحة ديناميكياً مع حالة availability.

### المحادثات

- **MOB-FR-020:** يستطيع المستخدم إنشاء Conversation داخل Space باستخدام agent key.
- **MOB-FR-021:** يستطيع المستخدم عرض محادثاته paginated حسب Space وAgent.
- **MOB-FR-022:** يستطيع المستخدم تغيير عنوان المحادثة وحذفها.
- **MOB-FR-023:** يستطيع المستخدم تثبيت model route للمحادثة أو الرجوع لاختيار الوكيل الافتراضي.
- **MOB-FR-024:** يستطيع المستخدم عرض الرسائل وإرسال رسالة وحذف رسالة واحدة.
- **MOB-FR-025:** يعرض التطبيق الإجابة تدريجياً مع typing/streaming feedback.
- **MOB-FR-026:** يدعم التطبيق Markdown ومحتوى الرسالة المنظم والأدوار المختلفة.
- **MOB-FR-027:** يعرض التطبيق notices وtool calls وcitations بطريقة مفهومة.
- **MOB-FR-028:** يستطيع المستخدم نسخ محتوى قابل للنسخ وإعادة محاولة رسالة فاشلة يدوياً.
- **MOB-FR-029:** يستطيع المستخدم تثبيت ملفات جاهزة على محادثة وفك تثبيتها عند دعم تجربة RAG.

### التخصيص والعمل دون اتصال

- **MOB-FR-030:** يستطيع المستخدم اختيار العربية أو الإنجليزية مع RTL/LTR صحيح.
- **MOB-FR-031:** يستطيع المستخدم اختيار Light أو Dark أو System.
- **MOB-FR-032:** يحتفظ التطبيق بآخر بيانات مقروءة ومسودات الرسائل محلياً.
- **MOB-FR-033:** لا يعيد التطبيق إرسال mutations غير idempotent تلقائياً بعد اتصال غير مؤكد.

### التكاملات والإدارة

- **MOB-FR-040:** يستطيع المستخدم عرض connectors وإنشاء اتصال OAuth وفصله حسب الصلاحيات.
- **MOB-FR-041:** تعكس الواجهة قدرات الوكلاء والأدوات من الباك اند بدلاً من قائمة ثابتة.
- **MOB-FR-050:** يستطيع المدير البحث في المستخدمين وتصفحهم وعرض حالاتهم وأدوارهم.
- **MOB-FR-051:** يستطيع المدير تعطيل/تفعيل المستخدم وتعديل الأدوار وحذف الحساب مع سبب تدقيقي.

## 13. متطلبات غير وظيفية مستخرجة أو لازمة

- **الأمان:** لا مفاتيح مزودين ولا OAuth tokens ولا أسرار داخل التطبيق أو السجلات.
- **العزل:** لا يرسل العميل workspace ID كسلطة ملكية؛ الهوية والمساحة مشتقتان من token والسياق الخلفي.
- **الأخطاء:** دعم `application/problem+json` و`code` و`correlation_id` مركزياً.
- **الأداء:** القوائم الكبيرة تستخدم virtualization وpagination، ولا تُجلب رسائل كل المحادثات عند فتح الصفحة الرئيسية.
- **الاستجابة:** يجب ألا تتجمد الواجهة أثناء streaming أو uploads أو reconnect.
- **الوصول:** إضافة accessibility labels، أحجام لمس مناسبة، وتباين ألوان؛ هذه غير مطبقة بصورة كافية في التطبيق الحالي.
- **الاختبار:** اختبارات للوحدات الحرجة، وعقود API، وتدفقات المصادقة والمحادثة والعمل دون اتصال؛ التطبيق الحالي لا يحتوي مجموعة اختبارات واضحة.
- **الرصد:** تسجيل أخطاء خالٍ من البيانات الحساسة مع correlation ID، وإضافة crash reporting بقرار منفصل.
- **التهيئة:** عناوين API وWebSocket وFirebase تأتي من environment/config موثق، لا من ثابت داخل المصدر.

## 14. أمور لا تُنقل حرفياً

- Axios calls الموزعة داخل الشاشات.
- API قديم مثل `/users/`, `/agents/{id}/chat`, `/users/{id}/agents`.
- إنشاء وتعديل وحذف Agent ككيان يملكه المستخدم.
- معرفات SQLite من نوع INTEGER للكيانات الخلفية.
- افتراض أن `message.content` نص.
- افتراض أن استجابة القوائم Array مباشرة؛ العقد الجديد يستخدم غالباً `{ data, meta }`.
- قائمة models الثابتة؛ ويوجد حالياً تضارب بين قائمة Dashboard وقائمة Chat.
- قائمة الأدوات الثابتة كمصدر حقيقة.
- الإرسال التلقائي للرسائل المعلقة.
- `usesCleartextTraffic: true` في إصدار الإنتاج دون حاجة موثقة.
- package ID القديم واسم Aivora غير المحسوم.
- بريد المدير المحمي المكتوب داخل الكود.
- رسائل الأخطاء العامة فقط من دون قراءة Problem Details.

- Firebase login/register/reset/logout وBearer token.

- Spaces.

- إنشاء/عرض/حذف/إعادة تسمية Conversations.

- حالات loading/empty/error/offline.
- cache قراءة ومسودات، دون auto replay.
- معالجة RFC 9457.

### P1 — مهم بعد استقرار الأساس

- تثبيت الملفات والاستشهادات لـRAG.
- WebSocket والإلغاء والإشعارات.

### P2 — مؤجل أو يحتاج API/قرار

- مزامنة mutations في الخلفية.

- media jobs وworkflows وMCP management ما لم تدخل نطاق المنتج الأول.

## 16. قرارات يجب حسمها قبل إغلاق وثيقة المتطلبات

1. هل الاسم النهائي AIZZAK أم Aivora؟ وما package ID النهائي؟
2. هل التحقق من البريد شرط للدخول إلى الباك اند الجديد؟
3. هل يحتاج التطبيق ملفاً شخصياً قابلاً للتعديل؟ إذا نعم، ما عقود الاسم والصورة؟
4. هل يسمح للمستخدم بحذف حسابه ذاتياً؟ وما نطاق حذف البيانات؟
5. ما Space الافتراضي للمستخدم الجديد، وهل ينشأ تلقائياً أم من التطبيق؟
6. ما Agents التي تظهر في الإصدار الأول، وما شكل input/content لكل Agent؟
7. هل «مسح المحادثة» يعني حذف Conversation أم حذف جميع رسائلها؟
8. هل حد الرسالة 4000 حرف ما زال مطلوباً؟ وما حد الخادم؟
9. هل SSE كافٍ للإصدار الأول أم WebSocket شرط إطلاق؟
10. ما صيغة deep link المعتمدة لعودة OAuth على Android؟
11. هل العمل دون اتصال للقراءة فقط مقبول للإصدار الأول؟
12. هل لوحة الإدارة جزء من تطبيق المستخدم نفسه أم تطبيق/واجهة منفصلة؟

## 18. النتيجة

التطبيق الحالي مفيد جداً كمرجع لتجربة المستخدم والهوية والحالات التفاعلية، لكنه ليس مرجعاً صالحاً لعقود البيانات الجديدة. عند كتابة وثيقة المتطلبات يجب اعتماد هذه الوثيقة لتحديد **ما يراه المستخدم وما يتوقعه**، واعتماد `openapi.yaml` و`api-specification.md` لتحديد **كيف تمثل البيانات وما يسمح به الخادم**. عند التعارض، لا يُنسخ السلوك القديم تلقائياً؛ يوثق القرار كمتطلب أو فجوة Backend أولاً.
