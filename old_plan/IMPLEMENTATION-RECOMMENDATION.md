# توصية بناء تطبيق AIZZAK Android الجديد

## الخلاصة

يُنصح ببناء التطبيق الجديد من الصفر داخل:

```text
C:\Users\anast\Desktop\aizzak-android
```

يتم نقل الهوية البصرية والمكوّنات القابلة لإعادة الاستخدام من التطبيق الحالي، مع عدم نسخ طبقة الاتصال أو قاعدة البيانات القديمة. السبب أن الباك اند الجديد لا يمثل مجرد تغيير في عنوان الخادم، بل يعتمد نموذجًا مختلفًا قائمًا على:

```text
Spaces → Agents → Conversations → Messages
```

بهذا الأسلوب نحافظ على مظهر التطبيق الحالي، ونمنع انتقال افتراضات الباك اند القديم إلى المشروع الجديد.

## التقنية المقترحة

- Expo SDK 56 وTypeScript.
- Expo Router للتنقل.
- `expo/fetch` أو `fetch` لطلبات الشبكة بدل Axios.
- TanStack Query لإدارة بيانات السيرفر، والترقيم، والتحميل، والأخطاء، وإعادة الجلب.
- Firebase Auth للمصادقة، مع إرفاق Firebase ID Token تلقائيًا بكل طلب محمي.
- SQLite فقط للتخزين المحلي الضروري، وليس كنسخة موازية كاملة من السيرفر منذ البداية.
- أنواع TypeScript مولدة من `openapi.yaml`، مع طبقة API مكتوبة يدويًا للتعامل مع SSE وWebSocket وأخطاء RFC 9457.

## الحفاظ على شكل التطبيق الحالي

لا يُنصح بنسخ ملفات الشاشات القديمة مباشرة؛ بعضها كبير ومختلط فيه التصميم مع استدعاءات الباك اند القديم. الأفضل تنفيذ الآتي:

1. استخراج الألوان، والمسافات، والخطوط، والبطاقات، والأزرار، والصور إلى Design System صغير.
2. إعادة بناء المكوّنات البصرية بنفس القياسات والمظهر.
3. توصيل المكوّنات بتدفقات الباك اند الجديدة من خلال طبقة API مستقلة.

للمحافظة على تجربة قريبة من التطبيق القديم:

- شاشة البداية تعرض محدد Space في الأعلى.
- بطاقات Dashboard تصبح Conversations بدل Agents.
- زر الإنشاء يفتح تدفقًا لاختيار أو إنشاء Space، ثم اختيار Agent، ثم تسمية المحادثة.
- تبقى شاشة Chat قريبة بصريًا من الحالية.
- تأتي قائمة النماذج من `/models` بدل قائمة ثابتة داخل التطبيق.

## مراحل التنفيذ

### 1. تأسيس المشروع والتصميم

- إنشاء مشروع Expo SDK 56 جديد باستخدام TypeScript وExpo Router.
- نقل الأصول والصور المطلوبة من التطبيق الحالي.
- إنشاء Theme موحد للعربية والإنجليزية، والوضعين الفاتح والداكن.
- بناء المكوّنات المشتركة مثل الأزرار، والبطاقات، وحقول الإدخال، ورسائل الخطأ، وحالات التحميل والفراغ.
- إبقاء ملفات `src/app` خاصة بالمسارات فقط، ووضع واجهات الشاشات والمنطق داخل `features` والمكوّنات.

### 2. المصادقة وطبقة API

- إعداد Firebase Auth للتسجيل وتسجيل الدخول والتحقق من البريد.
- انتظار اكتمال استعادة جلسة Firebase قبل تحديد شاشة البداية.
- إنشاء API client مركزي يضيف إلى كل طلب محمي:

```http
Authorization: Bearer <Firebase ID Token>
Accept: application/json
X-Correlation-Id: <uuid>
```

- عند استلام `401`، يُجدد Firebase token مرة واحدة ثم يعاد الطلب.
- استخدام `/me/context` للحصول على هوية المستخدم والأدوار والصلاحيات، بدل الاعتماد على حقول مثل `is_admin`.
- عدم تخزين Firebase ID Token يدويًا؛ Firebase يتولى تدويره وتجديده.
- تحويل أخطاء `application/problem+json` إلى نوع خطأ موحد يحتوي `status` و`code` و`correlation_id`.

### 3. التدفق الأساسي للبيانات

يُنفذ التدفق بهذا الترتيب:

```text
/me/context
    ↓
/spaces
    ↓
/agents + /models
    ↓
/conversations
    ↓
/conversations/{id}/messages
```

يجب إنهاء هذا المسار واختباره قبل البدء بلوحة الإدارة أو Gmail.

### 4. المحادثة

في النسخة الأولى:

- إرسال الرسائل بطلب JSON عادي دون بث.
- جلب سجل الرسائل باستخدام cursor pagination.
- تصميم حالات التحميل، والخطأ، والفراغ، والمحتوى.
- تحويل `MessageOut.content` من كائن API إلى نموذج عرض داخلي ثابت.
- عرض الخطأ مع `correlation_id` عند الحاجة إلى الدعم.

بعد استقرار النسخة العادية:

- إضافة WebSocket للبث الحي.
- التعامل مع أحداث `token` و`notice` و`tool_call` و`final` و`error`.
- إعادة الاتصال عند الإغلاق بالرمز `1013`.
- إعادة مزامنة المحادثة بعد استعادة الاتصال.
- دعم الإشعارات غير المتزامنة الخاصة بنتائج الفهرسة أو المهام عند الحاجة.

### 5. العمل دون اتصال

لا يُنصح بتكرار نظام Offline القديم مباشرة.

الإصدار الأول يجب أن يدعم:

- تخزين آخر المحادثات والرسائل للقراءة دون اتصال.
- الاحتفاظ بمسودة الرسالة محليًا.
- إظهار زر «إعادة المحاولة» عند فشل الإرسال.
- الاحتفاظ بالمحتوى القديم عند فشل عملية التحديث في الخلفية.

لا ينبغي إرسال الرسائل المعلقة تلقائيًا عند عودة الإنترنت؛ مسار الرسائل لا يدعم `Idempotency-Key`، وقد يؤدي الإرسال التلقائي إلى تكرار الرسالة إذا استلم السيرفر الطلب ثم انقطع الاتصال قبل وصول الرد.

### 6. الميزات الثانوية

بعد نجاح المحادثة الأساسية:

- تنفيذ لوحة الإدارة باستخدام `roles` و`status` و`online`.
- طلب سبب إداري عند تعطيل المستخدم أو حذفه أو تغيير صلاحياته.
- تنفيذ Gmail من خلال Connectors وConnections بدل المسارات القديمة الخاصة بالمستخدم.
- إضافة إدارة الملفات والمعرفة لاحقًا إذا كانت ضمن نطاق التطبيق.
- تنفيذ إعدادات الملف الشخصي فقط بعد توفر عقد API واضح لها.

### 7. الاختبارات والتحقق

- اختبارات لوحدة API client وتجديد token.
- اختبارات لتحويل `Problem Details` إلى رسائل التطبيق.
- اختبارات pagination وتحويل نماذج الرسائل.
- اختبار تسجيل الدخول البارد واستعادة الجلسة.
- اختبار فشل الشبكة أثناء إرسال رسالة ثم إعادة المحاولة.
- اختبار الأدوار والصلاحيات ومنع الوصول غير المسموح.
- اختبار اتجاه RTL والعربية والوضع الداكن.
- اختبار التطبيق على Android emulator وجهاز حقيقي قبل إنشاء نسخة الإصدار.

## إدارة إعدادات البيئات

يجب استخدام متغير واحد واضح للعنوان، وعدم تكرار إعداد العنوان في أكثر من ملف:

```text
EXPO_PUBLIC_API_BASE_URL=https://example.com/api/v1
```

مع ملفات أمثلة منفصلة للتطوير والإنتاج، وعدم وضع أي أسرار داخل متغيرات `EXPO_PUBLIC_*` لأنها تظهر داخل حزمة التطبيق.

## قرارات يجب حسمها قبل بناء النسخة الكاملة

1. عنوان API الفعلي لكل بيئة: development وstaging وproduction.
2. Firebase project وissuer اللذان يقبلهما الباك اند.
3. الشكل الرسمي للنص داخل `MessageOut.content`، وهل يكون مثل `{ "text": "..." }` دائمًا.
4. هل ينشئ الباك اند أو التطبيق Default Space تلقائيًا للمستخدم الجديد.
5. هل ستُنقل بيانات المستخدمين والمحادثات من النظام القديم، وكيف ستربط المعرّفات القديمة بالـUUID الجديدة.
6. مسارات تحديث الاسم والصورة وحذف الحساب الذاتي، لأنها غير موجودة في العقد الحالي.
7. Deep link الذي يعيد المستخدم من OAuth إلى تطبيق Android.
8. هل تُعرض Spaces مباشرة للمستخدم أم يستخدم التطبيق Space افتراضيًا مع إخفاء التعقيد.
9. السياسة المطلوبة للرسائل الفاشلة والعمل دون اتصال، بسبب غياب idempotency عن إرسال الرسائل.
10. تأكيد أن نسخة الباك اند المنشورة تطابق نسخة `openapi.yaml` الموجودة في وثائق المشروع.

## التقدير المبدئي

إذا كانت إجابات النقاط السابقة متوفرة والباك اند جاهزًا للاختبار:

- نسخة محادثة أساسية تعمل Online: نحو 3–5 أيام عمل.
- تكامل كامل مع الإدارة وGmail والتخزين المحلي: نحو 8–15 يوم تطوير.
- مع الاختبارات ومعالجة حالات الترقية والبيانات القديمة: قرابة 2–4 أسابيع لمطور واحد.
